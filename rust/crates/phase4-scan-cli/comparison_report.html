Why the contended Node run hit 760s

Verified by inspecting the live process tree mid-run, not inferred. Every heavy process traced back to ppid 10460 — the same validate-all request, not an unrelated job sharing the box.

Running concurrently, one request

  • pysemgrep — p/security-audit + p/owasp-top-ten
  • bearer — 8 processing workers
  • gitleaks detect
  • checkov
  • ORT/Gradle daemon + npm list — license/dependency resolution
  • spectral lint, codeql, trivy, syft, cosign, and more

Result

  • System load average peaked at 36.7 on a 14-core machine
  • Rust's run had those same 14 cores to itself
  • An identical earlier attempt via the ignite CLI timed out client-side at 5 minutes and kept running server-side unnoticed — the process list briefly showed two full scans stacked; that run was discarded and re-measured clean

Conclusions

✓

On the checks both engines share, Rust is roughly at parity today — not because the port is slow, but because the bottleneck isn't the orchestrator

359.9s (Rust) vs. 339.3s (Node's own Phase 4, idle machine) is a 6% gap in Node's favor, within measurement noise. Both numbers are dominated by the same external binaries — semgrep, CodeQL, Bearer, gitleaks — doing the same work on the same files. Whoever calls execFile on codeql database analyze doesn't change how long CodeQL takes to run. The orchestration language was never where this pipeline's wall time lived.

!

The 760s number is not evidence Node got slower — it's evidence of contention, confirmed by process inspection

Same request type, same repo, 2.1× the earlier idle-machine time. The process tree traced every extra cycle to legitimate concurrent work (ORT/Gradle/npm license scan) fighting the same cores as Phase 4's own tools, not to a regression in server.js. Comparing 365s against 760s as if they measure the same thing would be the wrong conclusion.

!

The real Rust opportunity hasn't been measured yet

The earlier Node report's own breakdown shows non-tool-bound, pure-compute checks costing real time on their own: secrets (211.8s, regex + gitleaks over 8,806 files), provenance (112.3s, tree-walk + hashing), euAiActDocuments (93.8s, a filename scan that shouldn't cost that much), health (92.6s). Those are exactly the kind of work a compiled implementation should cut hard — and they weren't isolated in either run above, since Node's total conflates them with tool-bound checks and Rust's run didn't include a staging step to compare against.

→

What's needed for a real verdict

phase4-orchestrator is check-engine-complete (33 checks, 42 crates total) but has no HTTP server, staging/copy step, ORT license-scan integration, or git/gh push path yet — it's not a drop-in replacement for server.js. A controlled rerun needs matched scope on both sides (add staging + ORT to Rust, or run Node with license-scan disabled) on an otherwise idle machine, back to back, same repo.
