Anomaly, root-caused (confirmed via source + per-tool subprocess logs)

Phase 4's total (118.9s) is 37.7s more than its own slowest individual check (semanticSast, 81.2s) — reproduced almost exactly on a second rerun (119.2s vs. 81.1s, a 38.1s gap). A third run with subprocess-level logging (RUST_LOG=info against a throwaway second server instance, not the numbers used elsewhere in this report) found the actual cause in rust/crates/phase4-orchestrator/src/lib.rs: secrets and governance are awaited inline, sequentially, before the big tokio::join! fan-out of the other 27 checks even starts — a leftover from how the checks are laid out in the function, not a concurrency bug. The log confirms it: gitleaks (secrets) starts alone at T+0s and runs solo for 31.3s; nothing else's tool probes fire until the instant secrets finishes. 35.8s (secrets) + 0.1s (governance) + 81.2s (concurrent block) ≈ 117.1s, matching the measured 118.9s almost exactly. Nothing in secrets or governance is a dependency of the other 27 checks — folding them into the same fan-out should recover close to the full 35.9s.

Correctness finding: CodeQL isn't actually scanning this repo

The original report attributed codeql's drop from 326.0s to ~5.5s entirely to the --threads=0 fix. The subprocess log shows a more important reason: on this run codeql invoked database create --language=java (auto-detected from real .java files under apps/meters/android/) and its Java autobuild failed outright — autobuild.sh exited 1 ("Spawned process exited abnormally") because no Java build toolchain is configured for that path — so the check logged "codeql done (4962ms) — 0 finding(s)" and moved on. No JavaScript/TypeScript database was even attempted in this run, despite that being the language the original report described CodeQL as covering. A failed autobuild reads identically to a clean scan in the pipeline's own output: 0 findings, check passed. That's a real coverage gap, not a performance win — worth either fixing the Java autobuild path (or switching that language to CodeQL's build-mode=none extractor, available in recent CodeQL CLI versions) or explicitly excluding java via CODEQL_LANGUAGES until it's fixed, so a language that can't be analyzed doesn't silently report as scanned-and-clean.

Reproducibility note

Two independent full reruns (unrelated to the subprocess-drilldown run above) landed within 0.4s of each other on total time and found the identical 79 blocking findings both times — the pipeline's timing and results are stable run-to-run on an otherwise idle machine. One difference did surface: packageHallucination dropped from 23.2s to 0.0s on the second rerun, everything else holding within 1–2s. Most likely a warm cache on the npm/PyPI/crates.io existence-check results from the first run — worth confirming in phase4:packageHallucination's own code before relying on it, since a 23s-per-cold-run cost reappearing on every fresh staging directory would matter for CI/pre-push usage where that cache may not persist between runs.

Node-era history (context, superseded by the numbers above)

The original version of this report measured the old Node server.js implementation (365s baseline, then 302s after four fixes: CodeQL --threads=0, a shared file-walk cache, a .angular build-cache exclusion, and CodeQL's LGTM_INDEX_FILTERS). That server no longer exists — it was deleted in cdf4d9d once the Rust port was complete (tagged stable_node_impl on GitHub for reference). The CodeQL threads and build-cache exclusion fixes both carried over into the Rust port and their effect is visible above (codeql 326.0s → 5.5s, secrets 211.8s → 35.8s). Full detail on those four fixes is preserved in this file's git history (git log -p -- performance_report.html) rather than repeated here.

Remaining levers

Both remain user-configurable without any code change, and neither is touched by default — dropping coverage is a security decision, not a performance one.

•

SEMGREP_CONFIG / security.semgrep.config

semanticSast (81.2s) is the confirmed critical path on this run. The prior, Node-era measurement of this same lever found dropping p/owasp-top-ten (keeping only p/security-audit) cut that check's time by ~64% with overlapping rule coverage — but the decision at the time was to keep both packs for functionality over wall-clock time. That decision has not been revisited for the Rust port; the lever is still there if the calculus changes for a specific environment (e.g. a fast inner-loop pre-push hook).

•

Fold secrets/governance into the main Phase 4 fan-out (~35.9s, root-caused above)

This is the biggest lever in this whole report and, unlike the semgrep tradeoff, it's free — no coverage lost. phase4-orchestrator runs secrets and governance sequentially before starting the tokio::join! over the other 27 checks, for no dependency reason found in the code. Moving them into the same fan-out should take Phase 4's wall time from ~118.9s toward ~81.2s (its slowest real check), cutting total pipeline time from ~131.7s to roughly ~94s.

•

Exclude non-source assets from semgrep's targets (~24s of the 78s, real)

See "Why semanticSast actually takes 78s" above — 10 vendored/generated files (emoji JSON assets, captured HTML snapshots) burn 39% of semgrep's scanning CPU-time for zero security value. Adding libs/cdn/src/assets/ and docs/design/captured/ (or a general large-single-line-file heuristic) to semgrep's excludes is a real, zero-coverage-loss fix — smaller than the secrets/governance fix above, but stacks with it.

•

Fix or exclude CodeQL's Java autobuild

Not a speed lever — a correctness one found while chasing the timing data. See the correctness finding above: CodeQL is currently reporting "0 findings" on a language it never successfully analyzed. Fixing the Java build path (or excluding java via CODEQL_LANGUAGES until it's fixed) matters more than any of the timing numbers in this report.
