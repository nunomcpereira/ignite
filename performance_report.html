What each cost is actually paying for

CheckTimeWhat it did
semanticSast339.2s Semgrep run with two rulesets back to back (p/security-audit + p/owasp-top-ten) over the whole tree. This is the single biggest cost in the run — two full registry rulesets on ~950k LOC.
codeql326.0s Builds a fresh CodeQL database and runs security-extended per language. Only JS/TS applied here, but building + analyzing one language database from scratch on this codebase alone takes ~5.5 minutes — a second or third language (Python/Java/Go) would run concurrently but each adds its own multi-minute database build.
secrets211.8s Regex + gitleaks pass over 8,806 text files — the single largest file count of any check, since it can't skip non-code assets the way SAST tools do.
provenance112.3s Built-in git/commit provenance record — no external tool, so its cost is pure tree-walking + hashing over the full 59.5k-file staged copy.
piiDataFlow109.5s Bearer's own git bootstrap (ensureGitContextForBearer: init + commit + fake origin) plus a full security-report scan, filtered down to PII categories after the fact.
euAiActDocuments93.8s A pure filename/path scan should be near-instant; at 93.8s it's walking all 59.5k staged files rather than a pruned subset — the biggest single anomaly in this run relative to what the check actually does.
packageHallucination78.7s 257 manifest dependencies, each a live HTTP existence check against npm/PyPI/crates.io — six workspaces means six package.json files' worth of dependencies checked one registry round-trip at a time.

What was fixed, and what it actually did

Four fixes shipped and were each verified with a real rerun of this same scan. Net result: 365s → 302s (17% faster), short of the 50% target. The two remaining large costs (semgrep's semantic SAST at 275s, CodeQL at 219s) are both rule-engine work scaling with real LOC and rule-set size — the honest remaining lever is trimming rule coverage, not a free engineering win.

FixVerified effect
CodeQL --threads CodeQL's CLI defaults to 1 thread when --threads is omitted (confirmed against the real CLI's own --help) — not "one per core" as the code's own comment assumed. Now always passes --threads=0 (all cores). Isolated effect: 326s → 64s on a clean run (a real ~5× speedup on that one check); on later runs sharing the machine with everything else this varied 60–220s — a real, safe fix, but its wall-clock payoff depends on how much else is competing for cores at the time.
Shared file-walk cache ~10 of Phase 4's built-in checks each called walkFiles independently, re-walking the same 59.5k-file tree from scratch, all concurrently. Now walked once per staged root and cached (invalidated when the staging dir is torn down in all three pipeline entry points). Reduces redundant I/O contention across the board.
.angular build-cache exclusion Discovered that .angular (Angular CLI/Vite's own bundled dependency cache) held 592k of 950k total scanned lines (62%) — vendored, minified copies of date-fns/firebase/express, not project source. Added to SKIP_DIRS (fixes every built-in check + gocloc for free) plus explicit --exclude/--skip-path flags for semgrep and Bearer, which do their own file discovery. Real, zero-coverage-loss fix — but net wall-time impact was smaller than the 62% figure suggested, since the real remaining ~358k lines of actual source still dominates.
CodeQL LGTM_INDEX_FILTERS codeql database create extracts from the whole --source-root itself — it never consulted Ignite's own SKIP_DIRS, so it was extracting .angular as if it were real source regardless of the fix above. Verified empirically that CodeQL's own **-glob syntax is rejected outright and a bare directory name is required; fixed and confirmed excluded via the database's source archive. Measured impact on this run was smaller than expected — CodeQL's cost here is dominated by real source volume, not vendor noise.

The one lever left: rule-set coverage vs. speed

Both remaining bottlenecks are already user-configurable without any code change, and neither was touched by default — dropping coverage is a security decision, not a performance one:

•

SEMGREP_CONFIG=p/security-audit (drop p/owasp-top-ten)

The two packs' rule coverage overlaps substantially (the codebase's own config comment says as much) — running only p/security-audit plausibly cuts this check well below its current 275s, at the cost of losing whatever OWASP Top 10-specific rules aren't already covered by security-audit. Not applied by default; not independently re-measured under the current usage budget.

•

CODEQL_LANGUAGES=javascript (narrow scope)

Already-configurable; only relevant on a repo with multiple CodeQL-supported languages present (this one only has JS/TS). No effect here, but relevant guidance for other projects.
