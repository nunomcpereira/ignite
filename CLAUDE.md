# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Ignite is a compliance gatekeeper for onboarding code into a GitHub org: upload a project (ZIP or folder) via a single-page app, or drive it headlessly (CLI/pre-push hook/MCP), and it runs a multi-phase pipeline — structure audit, secret scan, AI-governance audit, local LLM deep-scan, 20+ Phase 4 security/compliance checks, org governance CI (via `act`), unit tests — provisioning + pushing to GitHub only if every phase passes (or flagged issues are explicitly overridden with justification). Full pipeline/phase/check documentation lives in `README.md` (`../README.md` from `rust/`) and `docs-site/docs/` — read those for the "what does check X actually detect" level of detail; this file covers where things live and how to build/run/test.

## The implementation is 100% Rust — there is no Node code

Everything lives under `rust/` (67 crates). The original Node implementation (`server.js`, `auth.js`, `db-store.js`, `override-engine.js`, `mcp-server.js`, `guidelines-api.js`, `routes/`, `lib/`, `checks/`, `guidelines/`, `bin/`, `test/`) was deleted in `cdf4d9d` (2026-08-30) once the port was structurally complete and its scan-comparison against the Node original (tadone, file:line-exact parity) had already run and passed. The last-known-good Node state is tagged `stable_node_impl` on GitHub if a historical reference is ever needed. `docs-site/`, `vscode-extension/`, and `e2e/` are unaffected (client/tooling, not the server). Don't propose Node commands, `npm`, or Node file paths for anything server-side — there is nothing there to run.

**Crate-to-concept mapping:** almost every `rust/crates/<name>` crate corresponds 1:1 to one Node module/check and says so in its own `lib.rs`/`main.rs` top doc comment (e.g. `ignite-secrets`: "Faithful port of `checks/secrets.js`"). If you're looking for a specific check or subsystem, `grep -rl "Faithful port of" rust/crates/*/src/lib.rs` plus the crate name is almost always faster than guessing — the doc comment names the exact historical Node file for anyone who wants that context, and `rust/MIGRATION_STATUS.md` has a running log of every real behavioral finding/fix made during the port (not just "ported", but where the Rust and Node behavior genuinely diverged and why).

Notable crates:
- **`server`** (bin `ignite-server`) — the axum HTTP server. Routes live in `crates/server/src/routes/*.rs`, one file per endpoint group (`pipeline_validate.rs`, `pipeline_onboard.rs`, `pipeline_interactive.rs`, `sarif.rs`, `github_pr_status.rs`, `studio.rs`, `effectivate.rs`, `baseline.rs`, `runtime_coverage.rs`, `auto_fix.rs`, `issues.rs`, `history.rs`, `config.rs`, `dependencies.rs`, `reports.rs`, `github_annotations.rs`, `tools_status.rs`, `phase_meta.rs`, `job_issues.rs`, `fix_pr.rs`, `onboarded_repos.rs`). Serves the frontend (`../public/`, unchanged single-file SPA) as a fallback static service.
- **`cli`** (bin `ignite`) — `ignite scan [path]`, the CLI wrapper around `POST /api/pipeline/validate-all`.
- **`mcp-server`** (bin `mcp-server`) — MCP tools (`list_guidelines`, `check_guidelines`, `check_project`, `onboard_project`, `resolve_review_decision`, `effectivate_project`, etc.), stdio or HTTP transport.
- **`guidelines-api`** (bin `guidelines-api`) — loopback-only REST equivalent of the MCP guideline tools.
- **`create-api-key`** (bin `create-api-key`) — mints a headless API key for an existing user.
- **`phase4-orchestrator`** — fans out every Phase 4 check concurrently and normalizes results into `override-engine`'s issue shape (the Rust equivalent of `runPhase4Checks`).
- **`override-engine`** — the issue/override model: stable ids, severity scoring, override validation.
- **`db-store`** — the SQLite layer (`ignite.db`).
- **`config`** — `config.json`/env-var loading.
- **`tool-runner`** — every external-tool/`git`/`gh` subprocess invocation, with the same argument-array-only (no shell) sanitization the Node original had via `execFile`.
- **`github-api`** — shared `gh`-CLI-first/token-fallback GitHub operations (clone, PR create, commit status, etc.), used by the server's push path and by the standalone tools below.

## GHAS-bypass hardening (Rust-only, `rust/crates/`)

The pitch for dropping GitHub Advanced Security in favor of Ignite is only true if Ignite actually replaces what GHAS does automatically. Gaps closed so far:
- **`scheduled-rescan`** (`rust/crates/scheduled-rescan`): Dependabot-equivalent continuous coverage. Iterates every onboarded `(org, repo)` in `db-store`'s `projects` table, shallow-clones each one's current GitHub default branch, runs a real `POST /api/pipeline/validate-all` against a running Ignite server, and posts findings back via the existing `POST /api/pipeline/:jobId/github-check` path — only on a non-clean result; a clean scan just logs. HTTP client timeout defaults to 1800s (`IGNITE_SCHEDULED_RESCAN_TIMEOUT_SECS`), sized for real Phase 4 runs (5-16+ min per `rust/MIGRATION_STATUS.md`). Not wired into anything automatically — run by hand/cron/systemd, or a GitHub Actions `schedule:` trigger (example in `docs-site/docs/ci-integration.md`). Optionally chains straight into `auto-fix-pr` (below) on a non-clean result — see that entry for the opt-in env var.
- **`auto-fix-pr`** (`rust/crates/auto-fix-pr`, library crate `ignite-auto-fix-pr`): the Dependabot-parity gap `scheduled-rescan` itself leaves open — it detects a newly-disclosed CVE but never proposes the fix the way Dependabot's version-bump PRs do. Standalone CLI, dry-run by default (`--apply` to actually push/open PRs), same convention as `enforce-gate-branch-protection`. For each repo: shallow-clones the default branch, runs the real `dependency-vulnerability` scan (`ignite-dependency-license-scan`), resolves each finding's minimum fixed version via a real OSV.dev API call (deps.dev's own advisory schema, already used by that scan, has no per-package fixed-version field), and opens one PR per safe fix via `ignite-github-api`'s `gh_create_pr`. Deliberately conservative: only single simple version constraints are auto-edited (OR-ranges/wildcards/hyphen-ranges are left for a human), and a fix crossing a semver major version is always skipped, never silently applied. Idempotent via `git ls-remote --heads` on a deterministic per-(ecosystem, dependency, fixed-version) branch name.
  - **Auto-chained from `scheduled-rescan`**, opt-in via `IGNITE_SCHEDULED_RESCAN_AUTO_FIX` (unset/anything else = `off`, the default — an existing deployment's behavior never changes silently). `dry-run` discovers fix candidates and logs the plan without pushing; `apply` actually pushes branches and opens PRs. When enabled, `rescan_one` (`crates/scheduled-rescan/src/lib.rs`'s `run_auto_fix`) calls this crate's `discover_fix_candidates`/`apply_fix` directly against the checkout it already cloned for the rescan itself — no second clone — right after finding a non-empty issue list and before posting the commit status, so the commit status a human reads already reflects any fix PR just opened.
  - **Routine (non-vulnerability) dependency updates** (`--include-routine-updates`, CLI-only, opt-in — never auto-chained from `scheduled-rescan`): Dependabot's other half — `discover_routine_update_candidates` walks every manifest `ignite-studio-manifests` parses, resolves each dependency's current version (lockfile-pinned if present, else `best_effort_version` off the declared range), looks up the latest published version via `DepsDevClient::fetch_version_list`, and proposes a bump to the highest non-prerelease semver strictly newer than current — with no advisory driving it at all. Shares every mechanic with the vulnerability path (`FixCandidate.kind: FixKind`, `apply_fix`, lockfile regeneration, major-bump-always-skipped, per-(dep,version) branch idempotency); only PR title/body/commit-message wording differ (no advisory/OSV.dev references — `chore(...)` commit prefix instead of `fix(...)`).
  - **Dependabot `groups:` config parity** (`--group-by ecosystem`, CLI-only, opt-in — never auto-chained from `scheduled-rescan`, same posture as `--include-routine-updates`): without it, every fix candidate opens its own PR, which floods a stale/legacy repo with dozens of PRs on one run — the gap flagged against real Dependabot behavior. `group_candidates` (`rust/crates/auto-fix-pr/src/lib.rs`) partitions the flat candidate list into `(ecosystem, FixKind)` buckets — vulnerability fixes and routine chores are never bundled into the same PR even under grouping, since their commit-prefix/urgency genuinely differ. `apply_fix_group` is the multi-candidate counterpart to `apply_fix`: a singleton group is hand-delegated straight to `apply_fix` unchanged (byte-identical branch name/behavior to pre-grouping), so `--group-by` never alters output for a repo that only ever surfaces one candidate per ecosystem at a time. A real (2+ member) group gets one deterministic branch (`group_branch_name` — FNV-1a hash of the sorted `dep@version` set, so membership changes produce a new branch the same way `branch_name_for` does per-candidate), all its manifest edits applied onto one checkout before a single commit/push, and one PR (`pr_title_for_group`/`pr_body_for_group`, bullet-listing every bundled dependency). Per-member conservatism carries over unchanged: a major-bump candidate is excluded from its group (reported individually, never silently dropped), and a candidate whose manifest line no longer matches the scan is skipped without failing the rest of the group.
- **`enforce-gate-branch-protection`** (`rust/crates/enforce-gate-branch-protection`): standalone CLI, dry-run by default (`--apply` to actually change anything), that requires the `ignite/gate` status check and blocks direct/admin-bypass pushes on a repo's default branch via `gh api` (argument arrays, no shell). Not wired into any pipeline path — an operator runs it deliberately.
- **CodeQL query-suite pinning** (`config.example.json`'s `security.codeql.querySuites`): pinned to explicit query-pack versions instead of an unpinned `security-extended` reference — dropping GHAS means losing GitHub's continuously-updated CodeQL packs, so the ruleset is static until a human re-pins it. `reviewCadenceDays`/`lastReviewedAt` drive a non-blocking server-startup warning (`ignite-config::is_codeql_review_overdue`) when the pin is unset or stale.
- **Doc-only note**: even when dropping the rest of GHAS, keep GitHub's basic secret-scanning push-protection on — it's the one pre-receive capability Ignite's post-hoc scan structurally can't replace (a secret pushed then deleted in a follow-up commit was still exposed in the window between). Flagged as something to verify against the real GitHub bill, not a settled pricing fact. See `docs-site/docs/ci-integration.md`.
- **Native GitHub UI parity (SARIF + Dependency graph)**: findings/dependency data previously lived only in Ignite's own UI — GHAS surfaces both in GitHub's own Security/Insights tabs. `rust/crates/github-api`'s `gh_upload_sarif` (`POST repos/{full}/code-scanning/sarifs`, gzip+base64 per GitHub's API contract) and `gh_submit_dependency_snapshot` (`PUT repos/{full}/dependency-graph/snapshots`, GitHub's Dependency Submission API schema) push to those tabs. Both are wired into `POST /api/pipeline/:jobId/github-check` (`rust/crates/server/src/routes/github_pr_status.rs`) — the same call a pre-push hook/CI already makes to post the `ignite/gate` commit status, since that's the one place `(owner, repo, sha)` are already validated together against a commit guaranteed to exist on GitHub. The SARIF doc reuses `ignite-sarif::build_sarif` against the job's issues; the dependency snapshot reuses `ignite-dependency-license-scan::build_dependency_graph_snapshot` against `DbStore::get_dependency_scan_cache`'s cached scan (no second scan). `ref` is an optional field on the `github-check` request body — falls back to the repo's current default branch when omitted. Both pushes are best-effort/non-fatal (logged via `tracing::warn!`, never fail the gate-status response) and independently toggleable: `security.codeScanning.enabled` / `security.dependencyGraph.enabled` in `config.json` (`CODE_SCANNING_ENABLED`/`DEPENDENCY_GRAPH_ENABLED` env overrides), both on by default.
- **Git-history secret scan**: `ignite-secrets`'s built-in scan and its optional gitleaks supplement both only ever walked the current working tree — a secret committed then removed in a later commit stayed invisible, the one gap GHAS's own secret-scanning alerts (as opposed to push-protection) exist to catch. `run_gitleaks_history_scan` (`rust/crates/secrets/src/lib.rs`) runs `gitleaks detect` against full commit history (omitting `--no-git`, unlike the working-tree-only `run_gitleaks_scan`) — a no-op returning no findings when `root/.git` doesn't exist (an uploaded ZIP with no git history). Findings are tagged with a distinct tool name (`merge_gitleaks_history_findings` → `"gitleaks-history"`, vs. `"gitleaks"` for the working-tree run) and deduped against working-tree findings at the same file:line so a still-present secret isn't reported twice. Independent of `security.gitleaks.enabled`'s own working-tree gitleaks run: `security.gitleaks.scanHistory` in `config.json` (`GITLEAKS_SCAN_HISTORY` env override), default `false` — but `phase4-orchestrator::run_phase4_checks` (`rust/crates/phase4-orchestrator/src/lib.rs`) forces this on regardless of the config value whenever the run isn't in `fast` mode, since full runs (the default for the headless/pre-push/scheduled-rescan path) are exactly the case where the extra time is acceptable. The config default only actually matters for `fast` mode, which never runs it. Same pattern applies to `security.trivyImage.enabled` (the container-image `trivy image` scan, off by default for the same cost reason) — full mode forces that on too.
- **Private vulnerability reporting** (`rust/crates/report-vulnerability`, bin `report-vulnerability`): GHAS lets a maintainer privately draft a Security Advisory to coordinate a fix before public disclosure — Ignite's own `auto-fix-pr` (above) does the opposite by design, going straight to a public fix PR, so it can't cover this. Standalone CLI, same dry-run-by-default/`--apply` convention and `gh api ... --input <tmpfile>` mechanics as `enforce-gate-branch-protection` (nested JSON body, no shell). `report-vulnerability <org/repo> --summary <str> --severity <critical|high|medium|low> --ecosystem <eco> --package <name> --vulnerable-range <range> [--patched <version>] [--description <str>] [--cwe <id>]... [--apply]` creates a draft advisory via `POST repos/{full}/security-advisories`. Deliberately never wired into any scan/pipeline path — opening a private advisory is a judgment call about whether a finding needs private coordination at all, not something a scan should decide unattended.
- **GitHub Actions workflow security (zizmor)** — added after `ignite-guidelines`' narrow `no-unpinned-gha-action` regex check was found to only cover mutable-ref pinning, not the actually dangerous GHA classes (pwn requests, script injection, over-broad `permissions:`). Crate `rust/crates/gha-security` (`check_gha_security`, `GhaSecurityConfig`) wired into `phase4-orchestrator`'s concurrent fan-out; skips invoking `zizmor` entirely when a repo has no `.github/workflows/*.yml`. Config: `security.zizmor.{enabled,binary}` (`ZIZMOR_ENABLED`/`ZIZMOR_BINARY`), on by default. Issue category `gha-security` (CWE-829, OWASP A08:2021) in `override-engine`. No built-in fallback — needs zizmor's real workflow-expression parser.
- **Dependabot-style lockfile regeneration in `auto-fix-pr`**: a manifest-only version bump (the tool's original behavior) fails CI on any repo that enforces a matching lockfile — `regenerate_lockfile`/`lockfile_command` (`rust/crates/auto-fix-pr/src/lib.rs`) detect the ecosystem's lockfile next to the manifest (`package-lock.json`/`yarn.lock`/`pnpm-lock.yaml`, `Cargo.lock`, `go.sum`) and run the matching package-manager command (`npm install --package-lock-only`, `yarn install --mode update-lockfile`, `pnpm install --lockfile-only`, `cargo update -p <dep> --precise <version>`, `go mod tidy`) before committing, staging the lockfile alongside the manifest edit. `requirements.txt`/pypi and `pom.xml`/maven have no separate lockfile step (the manifest already is the pinned file, or there's no lock concept), so nothing runs for those. Best-effort: a failure (missing binary, network, resolution conflict) is folded into a warning in the commit message and PR body rather than failing the whole fix — `git`/`gh`/`npm`/`yarn`/`pnpm`/`cargo`/`go`/`poetry`/`pip-compile` are all in `tool-runner`'s `FIXED_COMMANDS` allowlist, resolved directly off `PATH`.
- **PR "Dependency Review" sticky comment**: GHAS-parity for `dependency-review-action`'s PR summary — `rust/crates/dependency-license-scan/src/dependency_diff.rs`'s `diff_dependency_scans`/`render_dependency_diff_comment` diff two cached `scan_json` snapshots (added/removed/version-changed/license-changed dependencies, rendered as collapsible markdown with tier badges) and post/update a single marker-tagged comment via `ignite-github-api`'s `gh_upsert_pr_sticky_comment` (lists existing PR comments, edits the one carrying `DEPENDENCY_REVIEW_MARKER` in place instead of accumulating one per push). Wired into `github_pr_status.rs`'s `github_check` handler alongside the SARIF/dependency-graph pushes — best-effort/non-fatal, only fires when `prNumber` is given. **Baseline caveat**: diffs against this project's own *previous* cached scan (`DbStore::get_previous_dependency_scan_cache`, populated by `save_dependency_scan_cache` shifting the old value on each overwrite), not a second clone-and-rescan of the PR's actual base branch — correct for the common case (a PR based on the org/repo's own last-scanned default branch), but can include unrelated changes when it isn't (see the module's own doc). Config: `security.dependencyReview.enabled` (`DEPENDENCY_REVIEW_ENABLED`), on by default.
- **Active secret verification** (`rust/crates/secret-verifier`, off by default): GHAS's secret-scanning partner program pings the issuing provider to tell a live leaked token apart from a dead/test one — `verify_secret`/`extract_secret_value` do the same for GitHub (`GET /user`), Slack (`auth.test`), and Stripe (`GET /v1/balance`), matched off the finding's `kind` (gitleaks' own rule id, e.g. `github-pat`) and the raw token pulled out of the finding's code snippet via the same publicly-documented token-format regexes gitleaks itself keys detection on. AWS (`sts:GetCallerIdentity`) is deliberately left unimplemented — needs SigV4 request signing, a materially riskier piece of crypto code to get right than a bearer-token GET. Every check is read-only/non-destructive and never logs the raw value. Wired into `phase4-orchestrator::run_phase4_checks`: when enabled, a `Live` result appends `" — VERIFIED LIVE"` to the finding's `kind` (surfaces in the issue summary, e.g. "Hardcoded github-pat — VERIFIED LIVE"); disabled (the default), nothing changes and no network call happens. Config: `security.secretVerification.{enabled,timeoutMs}` (`SECRET_VERIFICATION_ENABLED`), `enabled` defaults to `false` — sending a credential found in scanned code to a third-party API is an operator's explicit call to make, not a default a static-analysis check should opt into silently.
- **Code-scanning alert-dismissal sync**: previously one-directional — `gh_upload_sarif` creates GitHub Code Scanning alerts, but overriding the same finding in Ignite never touched GitHub's copy, so a justified/overridden issue kept showing as an open alert in GitHub's own Security tab. `find_matching_open_alert_number` (`rust/crates/server/src/routes/github_pr_status.rs`) matches an already-`"overridden"` `IssueRow` against `GithubApi::gh_list_code_scanning_alerts`' response by `rule.id` (the same `ignite_sarif::rule_id_for` mapping the SARIF upload used) plus the alert's most recent instance's file/line — GitHub's alerts API doesn't echo back SARIF's `partialFingerprints`, so this is the same file:line matching convention used elsewhere in this codebase (gitleaks/built-in dedup, override fuzzy-match). A match gets dismissed via `GithubApi::gh_dismiss_code_scanning_alert` (`dismissed_reason: "won't fix"`, `dismissed_comment` carrying Ignite's actual justification text). Runs right after the SARIF upload in `github_check`'s existing `code_scanning.enabled` block; best-effort/non-fatal like every other push there. Config: `security.codeScanning.syncDismissals` (`CODE_SCANNING_SYNC_DISMISSALS`), on by default whenever `codeScanning.enabled` is — only ever dismisses alerts backing an override Ignite itself already recorded, never based on unattended scan output. The GitHub→Ignite direction is now implemented too — see the next bullet.
- **Inbound code-scanning alert-dismissal sync (GitHub → Ignite)**: closes the direction the bullet above left open — a human dismissing or reopening a code-scanning alert directly in GitHub's **Security** UI previously never reached `ignite.db`, so the next `validate-all`/gate check kept treating the finding as an unapproved open issue. `POST /api/webhooks/github/code-scanning` (`rust/crates/server/src/routes/code_scanning_webhook.rs`) receives GitHub's `code_scanning_alert` webhook, verifies `X-Hub-Signature-256` (HMAC-SHA256) against `security.codeScanning.inboundWebhookSecret` (`CODE_SCANNING_INBOUND_WEBHOOK_SECRET`, unset by default — the endpoint 404s until a secret is configured, so an unconfigured deployment never exposes an unauthenticated write path), and maps the alert back to an Ignite issue with the same rule-id + file + line match `find_matching_open_alert_number` uses in the outbound direction. A `dismissed` delivery inserts an `overrides` row (`actor_email` sentinel `db_store::GITHUB_DISMISSAL_ACTOR_EMAIL`, justification drawn from GitHub's own dismissal reason/comment) via the existing `add_override`, then immediately flips that project's `issues.status` to `overridden` (`DbStore::set_issue_status`) rather than waiting for the next scan — and because `get_carry_forward_overrides` already reads across every past project of a repo, the same dismissal survives into the next real scan for free, no new carry-forward path needed. A `reopened` delivery removes exactly the override rows the webhook itself created (`DbStore::delete_github_dismissal_overrides`, scoped by the actor-email sentinel so a real human-justified Ignite override on the same issue id is never touched) and flips the issue back to `open` only if no other override still covers it (`DbStore::issue_has_override`). Not wired through `RequireAuth` — GitHub's webhook delivery has no Ignite session/API key; the HMAC check is the endpoint's only auth. Both directions emit an `audit-log` event (`code_scanning_alert.dismissed_on_github` / `.reopened_on_github`).
- **Inline PR review suggestions (Copilot Autofix parity)**: GHAS's Copilot Autofix posts inline PR review comments carrying a ```suggestion fenced block, which GitHub's diff viewer renders with a one-click "Commit suggestion" button — Ignite previously only offered leaving the PR entirely for a bulk fix-PR (`crates/fix-pr`) or a standalone `auto-fix-pr` run. `ignite_fix_pr::build_pr_suggestions` (`rust/crates/fix-pr/src/lib.rs`) turns a batch of `FixCandidate`s into one `PrSuggestion` per single-line edit (`start_line == end_line`) — deliberately narrower than the rest of fix-pr: it reuses the exact same conservative category set `SINGLE_LINE_FIX_CATEGORIES` (currently just `dependency-vulnerability`) that `narrow_snippet_for_edit` already restricts to one editable line, so nothing here ever proposes a suggestion wider than what `auto-fix-pr` already trusts itself to mechanically apply unattended. Wired into `github_check` (`rust/crates/server/src/routes/github_pr_status.rs`) alongside the SARIF/dependency-graph/dependency-review pushes, only when a PR number is present: filters the job's still-open issues to that category set, runs them through fix-pr's own `generate_fix_candidates` (no reimplementation of the LLM fix-computation), and posts each single-line result via `ignite_github_api::gh_create_pr_review_comment` (`POST repos/{full}/pulls/{pr}/comments`, GitHub's PR Review Comments API — `commit_id`/`path`/`line`/`side: "RIGHT"`). **Dedupe**: the Review Comments API has no PATCH-based upsert (unlike `gh_upsert_pr_sticky_comment`'s marker-edit trick for issue comments), so each suggestion's body carries a hidden `<!-- ignite:suggestion:<issue_id> --> ` marker and `gh_list_pr_review_comments` + `find_review_comment_marker` are checked first — an issue whose marker is already present on the PR is skipped outright rather than posted again on every push. Best-effort/non-fatal like every other push in `github_check`. Config: `security.prSuggestions.enabled` (`PR_SUGGESTIONS_ENABLED`), on by default — safe precisely because the scope is this narrow, same posture as `dependencyReview`.
- **Org-wide GitHub Ruleset enforcement**: `enforce-gate-branch-protection`'s original per-repo classic branch protection only protects a repo once someone remembers to run the tool against it by name — a newly-created repo in the org has no protection until then. `--org <org-name>` (repeatable, freely mixable with `<org/repo>` targets in one invocation) instead creates/updates an org-wide GitHub Repository Ruleset (`POST`/`PUT orgs/{org}/rulesets`, GitHub's newer API that applies to every current *and future* repo in the org) requiring the `ignite/gate` status check on each repo's default branch, blocking force-pushes/branch deletion, and requiring one reviewed PR — `bypass_actors: []` is the ruleset equivalent of `enforce_admins: true`, no one bypasses it. `find_existing_org_ruleset_id` looks up a ruleset already named `ignite-gate` first (`GET orgs/{org}/rulesets`) so a repeat run updates that ruleset in place (`PUT .../rulesets/{id}`) instead of creating a duplicate on every invocation. Same dry-run-by-default/`--apply` convention as the per-repo path; the org-ruleset payload's nested JSON goes through `GithubApi::gh_api_write`, which already detects a non-scalar field and routes through the raw REST fallback instead of mangling it through `gh api -f`.
- **Org ruleset drift detection/reconciliation**: the org-ruleset flow above only guarantees policy *at the moment it's applied* — an org-admin can still loosen the ruleset by hand afterwards (drop `ignite/gate`, add a bypass actor, delete a rule) directly in GitHub's UI, and the one-shot CLI has no way to notice until someone happens to re-run it. `--org <org-name>... --check-drift [--apply]` (`rust/crates/enforce-gate-branch-protection/src/main.rs`) turns it into a continuous check: fetches each target org's *current* ruleset (`GET orgs/{org}/rulesets/{id}`) and diffs it against the policy via `detect_ruleset_drift` — a pure function that checks the specific fields the policy cares about (enforcement, empty bypass_actors, and each of the four required rule types/parameters) rather than a byte-for-byte comparison, since GitHub's API echoes back extra server-assigned fields (`id`, `created_at`, per-rule ids) that would make an exact diff report drift on every call. Report-only by default (never mutates); pair with `--apply` to also reconcile (re-`PUT` the correct ruleset) whatever's drifted. Exit code is the signal a cron/CI caller watches: `0` clean, `2` drift found (even if `--apply` just fixed it — the caller wants to know drift *happened* this run), `1` on a lookup/apply error. Not wired into any scheduled path itself, same posture as the rest of this tool — run it from cron/a scheduled GitHub Actions workflow.
- **Custom secret patterns: playground + retroactive sweeper** (GHAS custom-pattern parity, `POST`/`GET /api/secret-patterns`): `ignite_secrets::test_pattern_against_sample` is the "playground" — compiles an operator-supplied regex and runs it against sample text, returning every match's position/text, so a pattern can be tried out before it's saved. No auth, no persistence (same posture as `routes/campaigns.rs`); Rust's `regex` crate's linear-time guarantee (no catastrophic backtracking, unlike PCRE behind GHAS's own editor) is why this is safe to run synchronously against arbitrary input — length/match-count caps exist for sane responses, not ReDoS. Saved patterns live in `db-store`'s `custom_secret_patterns` table (name/regex/enabled). `POST /api/secret-patterns/:id/sweep` is the retroactive half — GHAS custom patterns can check whether they'd have caught something already committed; `ignite_secrets::build_gitleaks_config_for_patterns` turns a pattern into a throwaway gitleaks TOML rule (`[extend] useDefault = true` keeps gitleaks' own built-ins active alongside it; the regex goes in a TOML literal string so it needs no escaping), and the sweep clones the target repo with full history (`GithubApi::gh_clone_repo_branch_full_history` — unlike every other clone site in this codebase, a shallow `--depth 1` clone would defeat the point) before running the existing `run_gitleaks_history_scan` against it. Requires auth (clones a real repo, spends a GitHub token) — same posture as `fix_pr.rs`'s `apply`. **Scope note**: an `enabled` pattern is not yet wired into the live working-tree/history scan path (`phase4-orchestrator`'s `SecretsConfig.gitleaks_config_path` is a single static operator-managed file, and merging DB-stored patterns into it per-job is unbuilt) — today this closes the *test-then-retroactively-check* half of GHAS custom-pattern parity, not automatic forward detection on every future scan.
- **Compliance audit packs** (`GET /api/compliance/audit-pack?from=YYYY-MM-DD&to=YYYY-MM-DD`, defaults to the trailing 90 days): SOC2/ISO27001-style evidence export — pure aggregation over data already collected for other features (`overrides`, `issue_first_seen`, `campaigns`), no new detection logic. `DbStore::list_overrides_in_range`/`mttr_by_severity_in_range` (`rust/crates/db-store/src/compliance.rs`) join `overrides` (who justified what, when, why — the change-management audit trail itself) against `issue_first_seen` (the same table `SlaConfig`'s breach math already reads) via SQLite `julianday()` arithmetic, the same pattern `sla.rs` already uses; an override whose `issue_first_seen` row has since aged out contributes to the count but not the avg/min/max (`NULL`, same as SQL's own aggregates ignoring it). The response bundles: overrides in the window (row-level evidence), MTTR-by-severity (explicitly labeled as time-to-formal-risk-acceptance, not time-to-fix — Ignite doesn't record a separate fixed-without-override timestamp), a live SLA-breach snapshot (`list_onboarded_repo_summaries`, not itself windowed — a point-in-time count is normal for this kind of control evidence), and campaign burndown (`list_campaigns`, as-is). API-only, no UI card yet, same posture as **Security campaigns** below.
- **SLA tracking & overdue-issue enforcement** (`ignite_config::SlaConfig`, on by default): GHAS-parity vuln-management SLA — an open issue that just sits unresolved is real risk regardless of whether a new scan ever re-flags it. `issue_first_seen` (`rust/crates/db-store/src/schema.rs`) records a per-`(org, repo, issue_id)` "first ever detected" timestamp, upserted/pruned every `replace_project_issues` call (`rust/crates/db-store/src/issues.rs`) — an issue that disappears (fixed/no-longer-open) and later reappears gets a fresh timestamp, not a stale one. Bucketed by `override-engine`'s existing 0-10 issue score (>=9 critical, >=7 high, else medium) against `sla.{criticalDays,highDays,mediumDays}` (`SLA_CRITICAL_DAYS`/`SLA_HIGH_DAYS`/`SLA_MEDIUM_DAYS`, defaults 7/30/90). `DbStore::list_onboarded_repo_summaries` surfaces a `slaBreaches` count per repo (rendered as a badge in `public/index.html`'s Onboarded Repos table); `DbStore::{count,list}_sla_breaches` give the same for one project. `scheduled-rescan` fails the sweep (`find_sla_breaches` in `rust/crates/scheduled-rescan/src/lib.rs`, reusing `GET /api/onboarded-repos` rather than a new endpoint) whenever any repo has an SLA breach, even on a run whose own scan came back clean — the finding isn't new, it just aged past its deadline.
- **Security campaigns** (`rust/crates/db-store/src/campaigns.rs`, `POST`/`GET /api/campaigns`, `POST /api/campaigns/:id/close`): a named, org-wide "burn down every open issue matching this filter (category + minimum score) by this date" tracker. `create_campaign` snapshots `initial_open_count` (every onboarded repo's latest scan, matching the filter) at creation time; `list_campaigns` recomputes the live matching count on every call, so `resolved_count = initial_open_count - <live count>` (clamped at 0) never drifts out of sync with overrides/fixes landing after the campaign was created — no separate progress-tracking write path to keep in sync. No UI card yet (API-only for now); the shape (`open_count`/`resolved_count` per campaign) is what a burndown chart would consume directly.
- **SIEM & audit-log streaming** (`rust/crates/audit-log`, off by default): GHAS's audit log API lets a security team stream governance events into their own SIEM — Ignite's own audit trail previously lived only in `ignite.db`. `ignite_audit_log::{AuditEvent, AuditSink, dispatch}` deliver a flat event (type/summary/severity/actor/org/repo/metadata) to configured HTTPS sinks: `generic` (raw JSON POST), `splunk_hec` (`{"event": ...}` + `Authorization: Splunk <token>`), `datadog` (`DD-API-KEY` header), or `cef` (CEF-over-HTTP text body, for ArcSight-style collectors). Config: `auditLog.{enabled,sinks[].{url,kind,token}}` (`AUDIT_LOG_ENABLED`, `AUDIT_LOG_SINKS` as a JSON array env override). `AppState::emit_audit_event` (`rust/crates/server/src/state.rs`) is the server-side call point — always `tokio::spawn`'d, fire-and-forget, so a slow/unreachable SIEM endpoint never adds latency to the triggering request. Wired at four event sites: override approved + gate passed with overrides (`routes/effectivate.rs`), push rejected on unresolved blocking findings (`routes/pipeline_onboard.rs`), and API key created (the standalone `create-api-key` binary, which blocks on a throwaway tokio runtime instead of spawning, since it's a short-lived CLI that should report accurately before exiting). An S3 sink is deliberately not implemented — needs SigV4 signing, the same reason AWS was left out of `secret-verifier`; a generic HTTPS collector fronting S3 already covers that case.

Prerequisites for full pipeline runs: Rust (stable toolchain), `git` on PATH, `gh` CLI authenticated (`gh auth login` / `gh auth status`) with repo-create permission in the target org. Optional: `act` + Docker for Phase 5 org governance CI and for multi-language unit tests (Docker images per language). Everything else — Trivy, Semgrep, gitleaks, GuardDog, Bearer, cosign, Syft, Checkov, hadolint, jscpd, gocloc, Spectral, picklescan, oasdiff, zizmor, CodeQL, ORT, licensee — is a soft dependency: every check soft-skips to a built-in fallback (or contributes nothing) when its tool is absent. `docs-site/docs/getting-started.md` has the one-shot install script (`scripts/install-tools.sh`) for all of them.

Some tests skip a real-binary/real-network end-to-end case via an early `eprintln!("skipping: ...")` + `return` rather than failing when the corresponding tool/Docker/network isn't available — this is expected in most dev environments; the fake-CLI/offline coverage in the same test files still runs regardless.

## Architecture

See `README.md`'s "System Architecture" diagram and "Pipeline Checks" table for the full request-flow/phase breakdown — it's accurate and Rust-only, and more detailed than what belongs here. In short: **three request paths, one set of phase-check functions** — the interactive browser upload (`POST /api/pipeline`, streaming NDJSON), the synchronous headless path used by the pre-push hook/CLI/CI (`POST /api/pipeline/validate-all`, phases 1-5 only, never ships), and the MCP path (a thin proxy from the standalone `mcp-server` binary to the same HTTP API — the MCP process itself never runs `git`/`gh`).

**File lifecycle:** upload → staging directory (per-job UUID, zip-slip/bomb-guarded extraction, isolated under the OS temp dir, `rust/crates/staging`) → scanned in place → pushed from staging → forcefully removed in a `finally`-equivalent regardless of outcome, so no user code lingers on disk.

**Issue/override model** (`rust/crates/override-engine`): raw findings from every Phase 3/4 check are normalized into a flat list of addressable issues, each with a stable id (`<category>::<file>::<line>`) and a 0-10 severity score. Blocking (`severity: error`) issues need a matching override with justification, or a source fix, to pass. Overrides require attribution and are persisted to the audit log.

**Storage** (`rust/crates/db-store`): single SQLite db (`ignite.db`, gitignored) — users, sessions, api_keys, github_connections, projects, overrides, file/CodeQL scan caches, issue baselines, runtime coverage.

**Auth** (`rust/crates/auth` + `server/src/auth*.rs`): pluggable via `AUTH_MODE` — `standalone` (scrypt-hashed accounts, default), `oidc`, or `github`. Headless callers (agents/CI) use an `Authorization: Bearer ignite_<key>` API key instead of a session cookie (`create-api-key` mints one).

## Configuration

Settings live in `config.json` at the repo root (`config.example.json` is the template, `IGNITE_CONFIG_DIR` tells the server where to find it — defaults to cwd); environment variables override individual keys — see `.env.example` for the full list. `config.json` and `.env` are both gitignored and contain this developer's real org name, SMTP creds, etc. — don't commit them.

## White-label branding (`public/branding.config.js`)

`public/index.html` never hardcodes brand values (product name, page title, header logo, support link, the `brand` accent color scale) — it reads them all from `window.IGNITE_BRAND`, defined by `public/branding.config.js` and merged over Ignite's own defaults (`DEFAULT_BRAND` in `index.html`'s `<head>`) so any key left out falls back to current Ignite branding unchanged. To apply a customer's brand, edit **only** `public/branding.config.js` — never edit brand values directly in `index.html`. This keeps the two non-conflicting: upstream feature commits touch `index.html`'s structure/logic, a customer's branding touches only their own file, and `git pull`/merge never sees the same line change on both sides. `branding.config.js` ships checked in with an empty override object (see its own header comment for every available key and an example) — the VS Code extension's own icon/name isn't covered by this and would need a separate per-customer build if ever themed too.

## Internationalization (`public/i18n.js`)

`public/index.html` supports English/French/Portuguese/German for its **static UI chrome only** — buttons, labels, headers, modals, tooltips, placeholders. Server-generated text (phase titles/logs, finding summaries/categories/severities, CWE/OWASP ids, tool output, file paths, URLs, JSON, raw API error messages) is never translated; it comes from the Rust backend and stays exactly as the API sends it. Translations live in `public/i18n.js` (`window.IGNITE_I18N.translations`), keyed by locale then by dotted key (e.g. `upload.title`), with `en` as the source of truth. `index.html` picks up a locale by two conventions — never a hardcoded literal for in-scope UI copy:
- Static markup: a `data-i18n`/`data-i18n-title`/`data-i18n-placeholder` attribute naming the key, applied by `applyStaticTranslations()`.
- JS-rendered (template-literal) markup: an inline `t('some.key', vars?)` call at the render site.

The picker (header, next to the theme toggle) calls `setLocale()`, which persists to `localStorage['ignite-locale']` and re-applies `[data-i18n*]` elements immediately; already-open dynamic panels pick up the new locale the next time their own render logic runs, not retroactively — there's no global re-render-on-locale-change. When adding new UI copy, add the key to `i18n.js`'s `en` table (and ideally fr/pt/de too — a missing key falls back to `en`, then to the raw key itself, so an incomplete translation degrades gracefully rather than breaking).

## Hardening invariants (don't relax without a strong reason)

- Every archive entry's resolved path must stay inside the staging root (zip-slip); symlink entries are skipped and never followed (`rust/crates/staging`).
- Extracted size capped at 4 GB, upload capped at 1 GB (zip-bomb guard).
- Every `git`/`gh`/external-tool invocation goes through `rust/crates/tool-runner`'s `ToolRunner`, which only ever executes as an argument array (`std::process::Command`, no shell); org/repo names are validated against GitHub's naming rules before use in any command.
- Staging directories and uploaded ZIPs are always removed regardless of success or failure.
