## What this is

Ignite is a compliance gatekeeper for onboarding code into a GitHub org. A user uploads a project (ZIP or folder) via a single-page app; the server runs it through a multi-phase pipeline - structure audit, secret scan, AI-governance audit, local LLM deep-scan, org governance CI (via `act`), unit tests - and only provisions + pushes to GitHub if every phase passes (or flagged issues are explicitly overridden with justification).

Almost all backend logic lives in one file: **`server.js`** (~6000 lines). Read it with `grep -n` for the section you need rather than loading it wholesale - it's organized as one long sequence of helper functions followed by route handlers near the bottom.

## Commands

```bash
npm install
npm start                    # → http://localhost:51337
npm test                     # node --test test/*.test.js
node --test test/secrets-scan.test.js              # single test file
node --test test/secrets-scan.test.js -t "gitleaks" # single test by name pattern

npm run guidelines:mcp       # MCP server over stdio (mcp-server.js)
npm run guidelines:mcp:http  # same, MCP_TRANSPORT=http
npm run guidelines:api       # REST API on 127.0.0.1:8090 (guidelines-api.js)

node scripts/create-api-key.js <email> [label]   # mint a headless API key for an existing user
npx ignite scan [path] [--changed-files a.js,b.py] [--json] [--fast]   # CLI wrapper around validate-all (see bin/ignite.js)
```

Prerequisites for full pipeline runs: Node ≥22, `git` on PATH, `gh` CLI authenticated (`gh auth login` / `gh auth status`) with repo-create permission in the target org. Optional: `act` + Docker for Phase 5 org governance CI and for multi-language unit tests (Docker images per language); `gitleaks` binary for supplemental secret scanning.

`generateProvenance`/`digestProjectTree` (build/commit provenance — see below) are built-in, not a soft-dependency on an external tool; unlike the rest of Phase 4 they always run regardless of what's installed.

Also optional, all soft-dependencies feeding Phase 4 (see `checkIacSecurity`/`checkContainerImageVulnerabilities`/`generateSbom`/`checkImageProvenance`/`checkSemanticSast`/`checkPiiDataFlow`/`checkCodeDuplication`/`generateLocMetrics`/`checkApiSchemas`/`checkFeaturePosture`/`checkMaliciousDependencies` in server.js): `trivy`, `checkov`, `hadolint` (IaC/container), `trivy image` (built-container-image CVE scan - reuses the same `trivy` binary + a real `docker build`, off by default via `security.trivyImage.enabled`/`TRIVY_IMAGE_ENABLED`), `syft`, `cosign` (SBOM/supply-chain), `semgrep`, `bearer` (semantic/PII SAST), `jscpd`, `gocloc` (duplication/LOC metrics), `spectral` (API schema lint), `guarddog` (malicious-dependency heuristic scan, npm/PyPI). The Compliance & Feature Posture Engine (`checkFeaturePosture`) doesn't add a thirteenth binary - it reuses `semgrep`, just with its own `ignite-posture-rules.yaml` ruleset and `compliance.posture.enabled` toggle. None of these are required to run the suite or the server - every check soft-skips to a built-in fallback (or simply contributes nothing) when its tool is absent.

Some tests (gitleaks integration, the eleven external-tool/posture integration suites - `test/iac-scan.test.js`, `test/sbom-scan.test.js`, `test/cosign-scan.test.js`, `test/semgrep-scan.test.js`, `test/bearer-scan.test.js`, `test/metrics-scan.test.js`, `test/spectral-scan.test.js`, `test/posture-scan.test.js` - and the multi-language unit-test-runner tests in `test/unit-tests-multilang.test.js`) skip their real-binary end-to-end case via `t.skip()` rather than fail when the corresponding tool/Docker isn't available - this is expected in most dev environments; the fake-CLI coverage in the same files still runs regardless.

## Architecture

**Pipeline flow (server.js):** multer buffers the upload → zip-slip/bomb-guarded extraction into a per-job UUID staging dir under the OS temp dir → sequential phase checks run in place → if all pass, `git init/add/commit` + `gh repo create --private` + push from staging → staging dir and uploaded ZIP are deleted in a `finally` block regardless of outcome, so no user code lingers on disk.

**Progress transport:** the pipeline endpoint (`POST /api/pipeline`) keeps the HTTP response open and streams newline-delimited JSON events (`log`, `status`, `done`, `review_required`). The frontend (`public/index.html`) consumes this with `fetch` + `ReadableStream` - no WebSocket/polling.

**Three ways to drive the pipeline**, all sharing the same phase-check functions:
1. `POST /api/pipeline` - interactive, streaming NDJSON, used by the browser UI. Supports `dryRun` (skip provisioning/push after all checks pass) and pauses with `review_required` if overridable issues are found.
2. `POST /api/pipeline/validate-all` - synchronous JSON, phases 1-5 only (always skips shipping), takes a local `projectPath` instead of an upload. For agent/CI loops that want pass/fail without a real push. Also the CLI's (`bin/ignite.js`, `ignite scan`) only backing endpoint - the CLI is deliberately validate-all-only, never shipping, so it needs no auth. Accepts an optional `changedFiles: string[]` (project-relative paths) - narrows the `issues` array in the response to just those files (plus `totalIssueCount`/`filteredByChangedFiles: true`), for an agent's fix-verify loop that only wants to know "did the files I just edited get flagged" without re-triaging the whole project on every iteration. This is a response *view*, not a gate - every blocking issue project-wide still has to be resolved or overridden for the run to pass regardless of `changedFiles`. Filtering logic lives in `lib/issue-filter.js` (`filterIssuesByChangedFiles`), covered by `test/issue-filter.test.js`.
3. MCP tool `onboard_project` (via `mcp-server.js`) - thin proxy that calls `POST /api/pipeline/onboard` on a running Ignite server; the MCP process itself never touches `git`/`gh`. Takes `overrides`/`actor` up front in the same call (no separate resolve step needed for a run started this way).

Two more MCP tools cover flows `onboard_project` alone doesn't: `resolve_review_decision` proxies `POST /api/pipeline/:jobId/review-decision`, for resuming a run paused mid-flight via the *interactive* `/api/pipeline` endpoint (e.g. one a human started in the browser UI and handed off). `effectivate_project` proxies `POST /api/projects/:projectId/effectivate`, for the "check first, ship later" loop: call `onboard_project` with `dryRun: true`, inspect the returned issues over one or more turns, then call `effectivate_project` once satisfied - it provisions + pushes the exact already-validated snapshot without re-running phases 1-5. Both are thin proxies, same pattern as `onboard_project`; tests in `test/mcp-override-tools.test.js`.

**SARIF export (`GET /api/pipeline/:jobId/sarif`, `routes/sarif.js` + `lib/sarif.js`):** the same flat issue list `GET /api/pipeline/:jobId/issues` returns (secrets/governance/LLM/license/vuln plus all twelve Phase 4 external-tool checks and CodeQL), reshaped into SARIF 2.1.0 - one `run`, `driver.name: "Ignite"`, one SARIF `rule` per distinct issue `category`. `error`/`warning` severity maps to SARIF `level` directly; an issue a human has already overridden downgrades to `note` rather than disappearing, since it's still a real finding, just not an open blocker. Each result's `partialFingerprints.igniteIssueId` carries the existing stable `<category>::<file>::<line>` id, and CodeQL's `crossFile`/`chain` data is preserved in `properties` rather than flattened away. Deliberately excludes non-issue artifacts (SBOM, LOC metrics, posture report) - SARIF is a findings format, not a document format; those keep their own Studio document endpoints. Works for both a still-running job (reads `runningRuns`, same as the issues endpoint) and a completed one (reads the `issues` table via `store.getProjectIdByJobId`/`getProjectIssues`).

**GitHub PR check/comment (`POST /api/pipeline/:jobId/github-check`, `routes/github-pr-status.js`):** posts a job's result back onto the GitHub commit it covers - a commit status (`context: "ignite/gate"`, success/failure) plus, when `prNumber` is given, one markdown summary comment - so reviewers see the gate on the PR itself instead of only whoever ran the scan seeing terminal/UI output. Reads the same live/store issue list `routes/sarif.js` does (same `runningRuns`/`getProjectIdByJobId` lookup). Token resolution mirrors the push path: `auth.resolveGithubToken(req)` (connected session) falling back to `resolveServerGithubToken()` (`GH_TOKEN`/`GITHUB_TOKEN` env) for unattended CI callers with no session. `ghCommentOnPr` (`lib/github-api.js`) is the one new GitHub call this adds - PR comment bodies are multi-line markdown, which can't go through `runTool`'s CLI-arg sanitizer (rejects `\n` in any argument), so the `gh` CLI path writes the body to a temp file and uses `--body-file` instead of `--body`; the token-only REST fallback (`POST /repos/:fullName/issues/:prNumber/comments` - PR comments are issue comments under GitHub's REST model) has no such restriction. See `docs-site/docs/ci-integration.md` for a sample GitHub Actions workflow and the companion agent self-fix-loop pattern (already possible today via `validate-all`'s `changedFiles` + `issues[]` - no new API surface, just documented as a loop).

**Fast/"lightning" Phase 4 mode (`fast: true` on `validate-all`, `ignite scan --fast`, `IGNITE_FAST_SCAN=true` on the pre-push hook):** `runPhase4Checks(..., { fast })` narrows the concurrent task batch to `FAST_MODE_TASKS` (secrets, AI-governance, file-encapsulation, semantic SAST/semgrep - the only checks cheap enough not to defeat the purpose of a pre-push hook), skipping CodeQL/Bearer/Trivy/GuardDog/Cosign/etc entirely for that run. Every skipped check's slot in `byName` is simply absent rather than populated with a "skipped" placeholder - safe because `collectPhase4Issues` already treats every group past `secrets`/`governance` as optional (`if (group) ...`), the same shape as "tool not installed". A tradeoff, not free coverage: a fast pre-push/CI run still needs a full run somewhere in the loop (real CI, or an occasional scan without `--fast`) to catch what lightning mode skips.

**Per-file scan caching:** Phase 4 checks (`checkSecrets`, `checkAiGovernance`, `checkLlmDeepScan` in server.js) are keyed by `{ org, repo }` passed down from the request, and cache per-file findings in the `file_scan_cache` SQLite table (`db-store.js`) keyed by `(org, repo, check_name, rel_path)` + content hash. A cache hit is a full-string match on `org` and `repo` - a typo'd or renamed repo name is a guaranteed full rescan even if the file content is identical to a previous run. The eleven external-tool checks added on top (IaC/SBOM/SAST/metrics/API-schema/malicious-dependency - see below) do **not** use this cache; each of those tools does its own whole-project discovery in one process invocation per run, so there's nothing per-file to memoize the way there is for the line-by-line regex/AST checks.

**Issue/override model (`override-engine.js`):** raw findings from secrets/governance/LLM checks (and the eleven external-tool checks below) are normalized into a flat list of addressable issues (`collectPhase4Issues`), each with a stable id (`<category>::<file>::<line>`) and a 0-10 severity score (`scoreForIssue`, independent of blocking/warning status). Blocking (`severity: "error"`) issues cannot be silently bypassed - they need a matching override with justification, or a source fix. Overrides require attribution (session user, or explicit `{email, name}` actor), trigger an email notification, and are persisted to the audit log (`overrides` table, surfaced per-project in the UI).

**Expanded diagnostic engine (IaC/supply-chain/SAST/metrics/API-schema/malicious-dependency, all inside Phase 4):** eleven optional external tools, each following the exact soft-dependency pattern gitleaks/ORT/licensee established - a `<tool>Tooling()` probe (`runTool('<tool>', ['--version'|'version'], ...)`), a `CONFIG.security|sbom|metrics|api.<tool>` block (`enabled`/`binary`/tool-specific options) with matching env-var overrides, and a check/generate function that soft-skips to a fallback (or to nothing, for tools with no meaningful heuristic substitute) on any missing-tool/parse failure:
- **IaC/container** (`checkIacSecurity`): Trivy is primary (`enabled: true` by default; falls back to a built-in Dockerfile heuristic - unpinned tag, missing `USER` - when unavailable); Checkov and hadolint are supplements merged in and deduped by `file+line+kind` (not line alone - different tools' rule catalogs routinely flag distinct issues on the same line).
- **SBOM** (`generateSbom`): Syft generates a CycloneDX SBOM, attached as a downloadable project document (`store.addUploadDocument`) - never an issue. Falls back to a minimal manifest-derived component list.
- **Image provenance** (`checkImageProvenance`): cosign verifies Sigstore signatures on Dockerfile `FROM` base images (on by default - a real network call per unique image, so `COSIGN_ENABLED=false` is there to opt out); unsigned images are always advisory.
- **Semantic SAST** (`checkSemanticSast`): Semgrep OSS, ruleset configurable (`security.semgrep.config`, default `p/security-audit`).
- **PII/GDPR data-flow** (`checkPiiDataFlow`): Bearer (on by default); needs real git remote/branch context that a fresh ZIP/folder upload doesn't have, so `ensureGitContextForBearer` bootstraps a throwaway one (init/commit + fake `origin` + `refs/remotes/origin/HEAD`) before invoking it. `bearer scan` with no `--report` flag defaults to Bearer's general "security" report (broad SAST - path traversal, weak crypto, etc.), not privacy-specific - findings are filtered to only those Bearer itself tags `category_groups: ["PII", ...]`, so a generic non-PII security finding never gets mislabeled as `pii-dataflow` (those already duplicate Semgrep's job).
- **Code duplication** (`checkCodeDuplication`): jscpd (off by default - the one exception among these ten; toggle via `metrics.jscpd.enabled`/`JSCPD_ENABLED`), always advisory (never blocks a run).
- **LOC metrics** (`generateLocMetrics`): gocloc, purely descriptive - attached as a document like the SBOM, never an issue.
- **API schema lint** (`checkApiSchemas`): Spectral has no directory-scan mode, so `discoverApiSchemaFiles` content-sniffs `.yaml`/`.yml`/`.json` files for a top-level `openapi`/`swagger`/`asyncapi` key rather than relying on filename. Ruleset defaults to the bundled `spectral-default-ruleset.yaml` (`spectral:oas` + `spectral:asyncapi`), overridable via `api.spectral.ruleset`/`SPECTRAL_RULESET`.
- **Compliance & Feature Posture Engine** (`checkFeaturePosture`, `CONFIG.compliance.posture`): reuses Semgrep's binary with a dedicated ruleset (`ignite-posture-rules.yaml`, `languages: [generic]` `pattern-regex`) to classify presence - not vulnerabilities - of SSO/RBAC/audit-logging/TLS/backups/encryption/rate-limiting as `DETECTED`/`PARTIAL`/`MISSING`. Never an issue; attached as `posture-report.json`. Falls back to `checkFeaturePostureFallback` (same weak/strong model, JS regex) when Semgrep is disabled/missing.

**EU AI Act coverage:** Ignite can only speak to the code-detectable slice of the Act - most of it (risk-management-system docs, conformity assessment, FRIA, human-oversight procedure) is an org-process artifact, not something a static scan sees. Two pieces cover what's actually detectable, both advisory-only (never block a run, never feed `collectPhase4Issues`):
  - Three extra `checkFeaturePosture`/`ignite-posture-rules.yaml` categories reuse the same DETECTED/PARTIAL/MISSING weak/strong model: `ai-act-prohibited-practice` (Art. 5 - biometric-categorization/emotion-inference/social-scoring libraries and call sites; unlike every other posture category, DETECTED here flags a *risk to review*, not a safeguard), `ai-act-transparency-disclosure` (Art. 13/50 - user-facing "AI-generated"/"you're talking to an AI" disclosure strings), and `ai-act-ai-logging` (Art. 12 - MLflow/W&B/LangSmith-style model input/output/decision logging, distinct from the general-purpose `audit-logging` category).
  - `checkComplianceDocuments` (`checks/compliance-documents.js`, `CONFIG.compliance.euAiActDocuments`, `EU_AI_ACT_DOCS_ENABLED`): a built-in, no-external-tool filename/path scan for the process-obligation documents the posture engine can't detect by code signature - risk-management-system doc (Art. 9), Annex IV technical documentation (Art. 11), an FRIA (Art. 27), a GPAI training-data summary/model card (Art. 53), a post-market monitoring plan (Art. 72). DETECTED/MISSING per category (no PARTIAL tier - there's no weak/strong distinction for "does this file exist"), attached as `ai-act-documents-report.json`. On by default; absence in this one repo's tree is not evidence the document doesn't exist org-wide (a GRC tool, a wiki, a separate compliance repo), so this is context for a human, never a gate.
  - **Advisory vs. findings toggle** (`CONFIG.compliance.euAiAct.reportAsFindings`, `EU_AI_ACT_REPORT_AS_FINDINGS`, false by default): whether the signals above actually surface as addressable/overridable issues (`collectPhase4Issues`) or stay purely descriptive in the two report documents. `false` (default) keeps them out of `collectPhase4Issues` entirely - `runPhase4Checks` (server.js) only calls the new `deriveEuAiActFindings(posture, documents)` helper when this is `true`, turning the three `ai-act-*` posture categories' matches and any `MISSING` document category into a `euAiAct` findings group fed through the same generic codebase-intelligence loop `deadCode`/`health`/`cssDeadCode`/`boundaries` use. Always `severity: 'warning'` regardless of the toggle - these are heuristic regex/filename signals, never promoted to a hard blocker.

Every one of checkov/cosign/bearer is **on by default** (flipped from their original off-by-default rollout) - set `CHECKOV_ENABLED`/`COSIGN_ENABLED`/`BEARER_ENABLED` to `false` individually to opt back out. `guarddog` (malicious-dependency heuristic scan, npm/PyPI) is likewise **on by default** - set `GUARDDOG_ENABLED=false` to opt out; it's the heaviest of the twelve fast-path tools (a real per-dependency registry fetch + static inspection), so environments with many manifest dependencies should expect Phase 4 to take noticeably longer with it on.

**Cross-file static analysis — CodeQL (`checkCodeqlCrossFile`, `checks/codeql-cross-file.js`, `CONFIG.security.codeql`):** the 13th soft-dep, and runs as part of `runPhase4Checks` (server.js) exactly like the other twelve — no separate opt-in path. Semgrep OSS's engine (`security.semgrep`) is intraprocedural/single-file, so a vulnerability whose tainted data crosses file/function boundaries (a stored-XSS or IDOR chain spanning a controller, a service layer, and a template) isn't reliably caught by anything else Ignite runs. CodeQL closes that gap by building a real per-language database (`codeql database create`) and running the bundled `security-extended` query suite (`codeql database analyze`). A database build is whole-project and can take minutes per language in isolation — but measured for real against Ignite's own codebase, it added only ~3 seconds to Phase 4's total wall time, since Phase 4 runs every check concurrently and CodeQL's build finishes well inside whichever other tool is already the long pole (typically Bearer). On by default as of that measurement, same as the always-on tools above — set `CODEQL_ENABLED=false` to opt out (e.g. if Bearer/Semgrep/GuardDog are disabled or fast enough on your codebase that CodeQL's own cost would become visible); `CODEQL_LANGUAGES` (default `javascript,python,java,go`) and `CODEQL_QUERY_SUITES` (JSON, per-language pack override) control scope. Findings carry a `crossFile` boolean — `true` only when the finding's SARIF `codeFlows` actually span more than one file (checked via `isCrossFileResult`), distinguishing genuinely new cross-file coverage from something Semgrep could plausibly have also caught. Per-language results are cached in `db-store.js`'s `codeql_scan_cache` table, keyed by `(org, repo, language, file_set_hash, codeql_version)` — `file_set_hash` is a content hash over every source file of that language (mirrors `manifest_scan_cache`'s content-hash approach, aggregated project-wide instead of per-manifest), so an unchanged codebase skips the full database rebuild on a repeat run of the same repo. Test file: `test/codeql-scan.test.js`.

**AI-era supply-chain/artifact checks (`checks/model-artifact-security.js`, `checks/api-schema-drift.js`, `checks/package-hallucination.js`):** three more Phase 4 checks, added to cover risk vectors specific to AI-generated/AI-assisted code that none of the checks above touch:
- **Malicious ML model artifact scan** (`checkModelArtifactSecurity`, `CONFIG.security.picklescan`): picklescan CLI soft-dep. Python's pickle format executes arbitrary code on load (`__reduce__`), and it's the on-disk format underneath `.pkl`/`.pickle` dumps and PyTorch `.pt`/`.pth`/`.bin`/`.ckpt` checkpoints — none of Ignite's source/manifest-focused scanners open these, so a poisoned weight file an agent downloaded or committed would otherwise sail through untouched. Deliberately excludes `.safetensors`/`.onnx` (neither is pickle-based — out of scope by design, not a gap). Findings are always `severity: 'error'` (category `malicious-model-artifact`, `CWE-502`) — an unsafe pickle global import executes on load, never advisory. No built-in fallback: needs picklescan's real opcode-level parser. On by default; `PICKLESCAN_ENABLED=false` to opt out.
- **API breaking-change / shadow-endpoint scan** (`checkApiSchemaDrift`, `CONFIG.api.oasdiff`): oasdiff CLI soft-dep, reuses `checks/api-schema.js`'s `discoverApiSchemaFiles` so both checks agree on what counts as an OpenAPI/AsyncAPI file. Where Spectral (`checkApiSchemas`) lints a spec in isolation, this diffs each discovered spec against its own previous git revision (`git show <prior-commit>:<path>` vs. the working-tree file, `oasdiff breaking --format json`) — catching a removed endpoint, a field that became required, a changed response type. Only meaningful with real git history to diff against (needs a clean working tree and a distinct parent commit, same precondition `checks/pii-dataflow.js`'s Bearer `--diff` mode has) — a fresh ZIP/folder upload with no prior commit has nothing to compare, so this simply contributes nothing rather than fabricating a baseline; it becomes active once a repo has been onboarded and is being re-scanned on a real push. `ERR`-level oasdiff findings map to `severity: 'error'` (category `api-breaking-change`), `WARN`-level to `warning`; the issue id's discriminator is the oasdiff change `id` (e.g. `api-removed-without-deprecation`), since every finding on one spec file otherwise collapses onto the same null-line issue id. On by default; `OASDIFF_ENABLED=false` to opt out.
- **AI package-hallucination / slopsquat detection** (`checkPackageHallucination`, `CONFIG.security.packageHallucination`): built-in, no external binary — a real HTTP existence check against npm/PyPI/crates.io's own registry APIs for every manifest dependency name (reuses server.js's `STUDIO_MANIFESTS` parse functions, the same list `generateSbom`'s fallback and `scanDependencyVulnerabilities` already parse). An LLM asked to write code routinely invents a plausible-looking package name that was never published ("slopsquatting") — an attacker who registers that exact name ships malware to the next dev/agent who installs whatever the AI suggested; this check is upstream of GuardDog's malicious-dependency scan (GuardDog inspects a package's contents once it exists, this asks whether it exists at all). Skips git/file/link/workspace-protocol version specifiers (never a real registry lookup). Existence results are cached in-process only (a `Map`, not `db-store.js`) — deliberately *not* persisted, since a stale "not found" surviving a process restart is exactly the failure mode to avoid. Deliberately excludes Go (no single central name registry — module paths are VCS URLs) and Maven (groupId:artifactId namespacing makes "does this exist" fuzzier than a flat name lookup). Always `severity: 'warning'` (category `package-hallucination`) — a private/internal package on a company registry looks identical to a hallucinated one from here, so this can never be a hard gate. On by default; `PACKAGE_HALLUCINATION_ENABLED=false` to opt out.

Test files: `test/model-artifact-security.test.js`, `test/api-schema-drift.test.js`, `test/package-hallucination.test.js`.

A separate opt-in "deep scan" endpoint (`POST /api/pipeline/deep-scan`) existed briefly during CodeQL's rollout — a distinct scan tier for already-onboarded repos, with its own clone-from-GitHub path since Ignite keeps no pushed repo's files on disk. Removed once real timing data showed the split wasn't earning its complexity: CodeQL on every push costs about the same as CodeQL never running at all, so there's no longer a meaningful "light vs. deep" distinction to expose as two separate flows — just one pipeline, with `security.codeql.enabled` as the single on/off switch.

**Path canonicalization gotcha (`relativeToRoot` helper, server.js):** external tools report their finding's file path inconsistently - some canonicize symlinks in the staging path (macOS's `/tmp` → `/private/tmp`, `/var` → `/private/var`; Spectral does this), others echo back exactly whatever path/cwd they were invoked with, uncanonicalized (Semgrep, in both `checkSemanticSast` and `checkFeaturePosture`). Diffing an uncanonicalized `root` against a canonicalized tool-reported path (or vice versa) produces a technically-valid but useless multi-`../` relative path - hit for real via a live pipeline run at the `/private/var/folders/...` staging root, not just theoretically. `relativeToRoot(root, targetPath)` fixes it once, generically, by `realpath`-ing *both* sides before computing the relative path - reach for it (not a bespoke `path.relative(root, path.resolve(root, ...))`) any time you're turning an external tool's reported path into a project-relative one.

**Ignite Studio's top bar surfaces every connected tool's output in one place** (`public/index.html`): a 📄 SBOM / 📊 LOC Metrics / 🛡️ Posture button per non-issue artifact (each backed by a new on-demand `GET /api/pipeline/:jobId/studio/{sbom,loc-metrics,posture}` endpoint, same live-recompute pattern the pre-existing 📦 Dependencies button uses), plus the project-wide issue summary bar's per-category labels became clickable filters (`studioSetCategoryFilter`) that narrow the file tree to one category's findings at a time - covering the other seven tools, whose findings already flowed into the same issue list secrets/AI-governance findings use.
- **Compliance & Feature Posture Engine** (`checkFeaturePosture`, `CONFIG.compliance.posture`): a different kind of check from the other nine - it classifies the *presence* of security/compliance features (SSO/SAML/OIDC, RBAC/ABAC, audit logging, SIEM forwarding, HTTPS/TLS, backups/DR, encryption at rest, rate limiting) as `DETECTED`/`PARTIAL`/`MISSING` per category, not error/warning issues, so it never feeds `collectPhase4Issues` - it's attached as a `posture-report.json` document instead (same as the SBOM/LOC-metrics artifacts). Fully conditioned on Semgrep (reuses `security.semgrep`'s binary/tooling probe - same CLI, a dedicated ruleset `ignite-posture-rules.yaml` and its own `compliance.posture.enabled` toggle): `>=1` "strong" (confirmed usage, e.g. `@PreAuthorize(`) match in a category is `DETECTED`; only "weak" (import/dependency-only) matches is `PARTIAL`; none is `MISSING`. `ignite-posture-rules.yaml` uses Semgrep's `languages: [generic]` `pattern-regex` mode deliberately - the question being answered ("does this codebase use framework X") is the same across all six target languages (TS/JS, Java, Go, Python, C#, Ruby), so one cross-language text-signature rule per category/tier is more maintainable than six near-duplicate AST rules. Soft-falls back to `checkFeaturePostureFallback` - the same weak/strong model as a JS regex sweep, kept in sync by hand - when Semgrep is disabled or not installed, logged as `Engine: Ignite Built-In Posture Scanner (Fallback)` vs. `Engine: Semgrep CLI vX.X (External Posture Scanner)`.

All twelve checks (eleven external tools, plus the posture engine that reuses Semgrep's binary rather than adding a twelfth) wire into the same three call sites `checkSecrets`/`checkAiGovernance` already do (`/api/pipeline/validate-all`, `/api/pipeline/onboard`, the interactive SSE pipeline) plus `/api/tools/status` and the UI's `TOOLS_META` panel in `public/index.html` - never Studio's rescan endpoint (network/process-heavy tools would make every edit-loop rescan slow). Each has its own test file (`test/iac-scan.test.js`, `test/sbom-scan.test.js`, `test/cosign-scan.test.js`, `test/semgrep-scan.test.js`, `test/bearer-scan.test.js`, `test/metrics-scan.test.js`, `test/spectral-scan.test.js`, `test/posture-scan.test.js`, `test/guarddog-scan.test.js`) covering config/env wiring, fake-CLI parsing/dedup/soft-fail, and a real-binary end-to-end case that self-skips when the tool isn't installed.

**Auth (`auth.js`):** pluggable via `AUTH_MODE` (env) / `auth.mode` (config.json) - `standalone` (local scrypt-hashed accounts, default), `oidc` (delegates to any standards-compliant IdP), or `github` (sign in with GitHub, which also connects that account for push). All modes converge on the same session-cookie + `req.user` shape that override attribution relies on. Auth is not required to browse or run the pipeline - only enforced where attribution matters (submitting an override without a session needs an explicit actor in the body, else `401`).

**Headless auth (API keys, layered on top of the above):** every `AUTH_MODE` requires a browser-driven OAuth/login redirect to establish a session - something no unattended agent/CI caller can complete, and `auth.resolveGithubToken(req)` (real, non-dryRun push) hard-requires `req.user`. `attachUser` (`auth.js`) closes that gap: after checking the session cookie, it falls back to an `Authorization: Bearer ignite_<key>` header, looked up by SHA-256 hash (not scrypt - these are already high-entropy random secrets, not user-chosen passwords, so there's no offline-guessing cost to slow down) against the `api_keys` table (`db-store.js`; `user_id`, `key_hash`, `label`, `last_used_at`, `revoked_at`). Session cookie wins if both are present. Keys are minted with `node scripts/create-api-key.js <email> [label]` for an *existing* user (this script never creates accounts - sign up/log in once via whatever `AUTH_MODE` is configured, first) and printed exactly once; `store.revokeApiKey(id)` (no route exposed yet, DB-only) invalidates one. `mcp-server.js`'s `proxyToIgnite` and `bin/ignite.js` both attach `Authorization: Bearer $IGNITE_API_KEY` automatically when that env var is set - unset, they still work for anything that doesn't need `req.user` (dryRun validate-all/onboard, read-only tools). Tests: `test/api-key-store.test.js` (db-store.js layer), `test/api-key-auth.test.js` (attachUser/requireAuth layer).

**Guidelines catalog (`guidelines/catalog.js` + `guidelines/checks.js`):** the same detection patterns Ignite's onboarding pipeline enforces (secret regex, AI-governance `.invoke()`/`.stream()` calls missing `recursion_limit`, injection sinks, insecure deserialization, etc.), exposed as a standalone checks engine so they can be applied during development, not just at onboarding. Consumed by `mcp-server.js` (MCP tools: `list_guidelines`, `get_guideline`, `check_guidelines`, `check_project`, `check_dependency_licenses`, `check_dependency_vulnerabilities`, `onboard_project`, `resolve_review_decision`, `effectivate_project`) and `guidelines-api.js` (REST equivalent, loopback-only by default since `/check-project` reads arbitrary host paths). `mcp-server.js` only `require('./mcp-server.js')`s cleanly for tests because `main()` is guarded behind `require.main === module` and `buildServer` is exported - requiring it unguarded would start a stdio transport as a side effect.

**Storage (`db-store.js`):** single SQLite db (`ignite.db`, gitignored) holding users, sessions, api_keys, github_connections, projects, overrides, and the file_scan_cache - all accessed through prepared statements returned by `createDbStore()`.

**Phase 4 org governance CI:** rather than reimplementing the central org's workflow logic, Ignite fetches the real `ai-guardrails-orchestrator.yml` from the governance repo via `gh api` and runs it locally with `act` against the staged project in Docker - so local pass/fail matches what a real PR would get. Soft-skips with a warning if `act`/Docker are unavailable (the workflows still gate remotely).

**Codebase-intelligence checks (dead code, complexity/health, architecture boundaries, CSS dead-class scan):** four more built-in, zero-external-tool checks wired into `runPhase4Checks` alongside the twelve above - closing a JS/TS-codebase-quality gap against tools like fallow.tools that Ignite's original secrets/governance/SAST focus didn't cover. All four are heuristic (regex/bracket-depth parsing over `lib/module-graph.js`'s lightweight import graph, not a real type-checker or build system), so every finding is always advisory (`severity: 'warning'`) - a human confirms before deleting/restructuring, never a hard gate.
- **Dead code / unused exports / unused deps** (`checkDeadCode`, `checks/dead-code.js`, `CONFIG.codeIntelligence.deadCode`): builds a module graph from `package.json`'s `main`/`module`/`exports`/`bin` plus test/config files as entry points, BFS-reaches every file transitively imported from there, and flags anything unreached (`unused-file`), any named export never imported anywhere by name (`unused-export`), and any `package.json` dependency never `require`/`import`-ed and not mentioned in an npm script (`unused-dependency`). Upgrades `unused-export` candidates to an AST-based check (`ts.createSourceFile`) when the *scanned project itself* has `typescript` in its own `node_modules` - filters out matches that were really inside a comment/string/non-export declaration the regex pass couldn't distinguish.
- **Complexity/maintainability health** (`checkComplexityHealth`, `checks/complexity-health.js`, `CONFIG.codeIntelligence.health`): per-file cyclomatic complexity (branch-keyword counting), cognitive complexity (nesting-weighted), a calibrated Maintainability Index (0-100; no Halstead Volume without a real parser, so coefficients are tuned against Ignite's own codebase rather than the textbook SEI formula), and a CRAP score (`CC² × (1-coverage/100)³ + CC`) that pulls real coverage from ingested runtime data when available (see below) and otherwise conservatively assumes 0%. `high-complexity`/`low-maintainability` findings use complexity *density* (decisions per line), not a raw per-file total, to avoid flagging every file over ~65 lines. Also computes git-churn-weighted hotspots and a ranked refactor-target list (not issues - descriptive only, same precedent as LOC metrics/posture).
- **Architecture/import-boundary enforcement** (`checkBoundaries`, `checks/boundaries.js`, `CONFIG.architecture.boundaries`): off by default (unlike the always-on three above - a default zone layout on a project that doesn't follow one would be pure noise). Opt in via `preset` (`bulletproof` | `layered` | `hexagonal` | `feature-sliced`) and/or custom `zones: [{ name, pattern, allow }]`; a file belongs to the first zone whose pattern matches (first-match wins), and single-`*` glob segments are captured so sibling instances of the same zone (e.g. `src/features/auth` vs `src/features/billing`, both zone `"features"`) are correctly treated as isolated from each other, not just from other tiers.
- **CSS/Tailwind dead-class scan** (`checkCssDeadCode`, `checks/css-dead-code.js`, `CONFIG.codeIntelligence.cssDeadCode`): flags a `.css`/`.scss`/`.less` class selector never referenced in any scanned `class`/`className` attribute. One-directional only - it cannot flag "unused Tailwind utilities" (those only exist if referenced in the first place); `is-`/`has-`/`js-`-prefixed classes are excluded (commonly toggled via `classList`, never appearing as a literal string this scan can see).

All four feed the same issue/override model as the twelve external-tool checks (`collectPhase4Issues` in `override-engine.js`, categories `dead-code`/`complexity-health`/`architecture-boundary`/`css-dead-code`).

**`.igniteignore` (`checkIgniteIgnoreCommitted`, `checks/igniteignore.js`, `CONFIG.ignoreFile`):** a project-root file, `.gitignore` syntax (parsed by `lib/fs-utils.js`'s `gitignorePatternToRegex`/`isGitignored` - the same machinery `.gitignore`'s own secret-leak exemption already used, generalized rather than duplicated), letting a project opt specific paths (generated code, fixture data, a vendored bundle) out of every Ignite check entirely. Enforced at exactly one choke point: `walkFiles` (`lib/fs-utils.js`) loads it once per top-level call and prunes a matching directory before ever descending into it, so all ~20 checks that discover files via `walkFiles` honor it automatically with zero per-check wiring. Unlike the four codebase-intelligence checks above, the one finding this produces is **blocking** (`severity: 'error'`, category `igniteignore-not-committed`) rather than advisory: a `.igniteignore` that exists on disk but was never committed to git is a silent, unreviewable scan bypass - a teammate looking at the repo on GitHub has no way to know some paths were never scanned, which is exactly what a compliance gatekeeper exists to prevent. Skips the check entirely (no finding either way) when the project isn't a git repo yet - a fresh ZIP/folder upload being onboarded for the first time has nothing to be "committed" against until server.js's own `git init && git add -A && git commit` runs right before push, which will include `.igniteignore` in that very first commit.

**Auto-fix** (`lib/auto-fix.js`, `POST /api/pipeline/auto-fix`): turns a subset of dead-code findings into a fix plan and (optionally) applies it. `unused-file` → delete; `unused-dependency` → remove the `package.json` entry; `unused-export` → narrow an `export { }` list if the export is one of those (declaration stays, just stops being exported) or falls back to a `manual` action - deleting a function/class/const body via regex with no real parser backing the edit is too easy to corrupt, so that's deliberately never automated. `dryRun: true` (the default) returns the plan without touching disk.

**Baseline/diff adoption mode** (`db-store.js`'s `issue_baselines` table, `lib/baseline-filter.js`, `routes/baseline.js`, `validate-all`'s `baselineMode` param): lets a large codebase adopt Ignite incrementally instead of needing every existing finding fixed/overridden on day one. `baselineMode: 'save'` runs the pipeline normally and snapshots whatever issue ids came out of it (typically called once, on a clean main-branch run); `baselineMode: 'gate'` narrows what actually blocks the run to issues *not* in the saved set - baselined issues still appear in the full `issues[]` response (tagged `status: 'baselined'`, same convention as `'overridden'`) so they stay visible, just not blocking. `POST/GET/DELETE /api/baseline/:org/:repo` manage a baseline directly (e.g. from CI, independent of a validate-all call).

**Runtime coverage ingestion** (`lib/runtime-coverage.js`, `db-store.js`'s `runtime_coverage` table, `routes/runtime-coverage.js`): the one place production truth enters Ignite's otherwise fully-static pipeline - a project's own CI POSTs whatever coverage report its test suite already produces (Istanbul `coverage-final.json`, or a simple `{ file: hitCount }` map) to `POST /api/runtime-coverage/:org/:repo`; `checkComplexityHealth` then uses real per-file coverage % in its CRAP score instead of the conservative 0% default. Ignite doesn't instrument the *target* project's own runtime itself (out of scope for an onboarding gatekeeper) - this is a receive-only endpoint, not an injected beacon.

## Configuration

Settings live in `config.json` next to `server.js` (`config.example.json` is the template); environment variables override individual keys - see `.env.example` for the full list (LLM scan URL/model/mode, governance repo/workflow, gitleaks toggle, SMTP/notifications, auth mode/OIDC settings, the eleven external-tool `enabled`/`binary`/tool-specific settings under `security.*`/`sbom.syft`/`metrics.*`/`api.spectral`, etc.). `config.json` and `.env` are both gitignored and contain this developer's real org name, SMTP creds, etc. - don't commit them.

## Hardening invariants (don't relax without a strong reason)

- Every archive entry's resolved path must stay inside the staging root (zip-slip); symlink entries are skipped and never followed.
- Extracted size capped at 4 GB, upload capped at 1 GB (zip-bomb guard).
- All `git`/`gh` invocations use `execFile` with argument arrays (no shell); org/repo names are validated against GitHub's naming rules before use in any command.
- Staging directories and uploaded ZIPs are always removed in a `finally` block, success or failure.
