# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Ignite is a compliance gatekeeper for onboarding code into a GitHub org: upload a project (ZIP or folder) via a single-page app, or drive it headlessly (CLI/pre-push hook/MCP), and it runs a multi-phase pipeline — structure audit, secret scan, AI-governance audit, local LLM deep-scan, 20+ Phase 4 security/compliance checks, org governance CI (via `act`), unit tests — provisioning + pushing to GitHub only if every phase passes (or flagged issues are explicitly overridden with justification). Full pipeline/phase/check documentation lives in `README.md` (`../README.md` from `rust/`) and `docs-site/docs/` — read those for the "what does check X actually detect" level of detail; this file covers where things live and how to build/run/test.

## The implementation is 100% Rust — there is no Node code

Everything lives under `rust/` (67 crates). The original Node implementation (`server.js`, `auth.js`, `db-store.js`, `override-engine.js`, `mcp-server.js`, `guidelines-api.js`, `routes/`, `lib/`, `checks/`, `guidelines/`, `bin/`, `test/`) was deleted in `cdf4d9d` (2026-08-30) once the port was structurally complete and its scan-comparison against the Node original (tadone, file:line-exact parity) had already run and passed. The last-known-good Node state is tagged `stable_node_impl` on GitHub if a historical reference is ever needed. `docs-site/`, `vscode-extension/`, and `e2e/` are unaffected (client/tooling, not the server). Don't propose Node commands, `npm`, or Node file paths for anything server-side — there is nothing there to run.

**Crate-to-concept mapping:** almost every `rust/crates/<name>` crate corresponds 1:1 to one Node module/check and says so in its own `lib.rs`/`main.rs` top doc comment (e.g. `ignite-secrets`: "Faithful port of `checks/secrets.js`"). If you're looking for a specific check or subsystem, `grep -rl "Faithful port of" rust/crates/*/src/lib.rs` plus the crate name is almost always faster than guessing — the doc comment names the exact historical Node file for anyone who wants that context, and `rust/MIGRATION_STATUS.md` has a running log of every real behavioral finding/fix made during the port (not just "ported", but where the Rust and Node behavior genuinely diverged and why).

Notable crates:
- **`server`** (bin `ignite-server`) — the axum HTTP server. Routes live in `crates/server/src/routes/*.rs`, one file per endpoint group (`pipeline_validate.rs`, `pipeline_onboard.rs`, `pipeline_interactive.rs`, `sarif.rs`, `github_pr_status.rs`, `studio.rs`, `effectivate.rs`, `baseline.rs`, `runtime_coverage.rs`, `auto_fix.rs`, `issues.rs`, `history.rs`, `config.rs`, `dependencies.rs`, `reports.rs`, `github_annotations.rs`, `tools_status.rs`, `phase_meta.rs`, `job_issues.rs`, `fix_pr.rs`, `onboarded_repos.rs`). Serves the frontend (`../public/`, unchanged single-file SPA) as a fallback static service.
- **`cli`** (bin `ignite`) — `ignite scan [path]`, the CLI wrapper around `POST /api/pipeline/validate-all`.
- **`mcp-server`** (bin `mcp-server`) — MCP tools (`list_guidelines`, `check_guidelines`, `check_project`, `onboard_project`, `resolve_review_decision`, `effectivate_project`, etc.), stdio or HTTP transport.
- **`guidelines-api`** (bin `guidelines-api`) — loopback-only REST equivalent of the MCP guideline tools.
- **`create-api-key`** (bin `create-api-key`) — mints a headless API key for an existing user.
- **`phase4-orchestrator`** — fans out every Phase 4 check concurrently and normalizes results into `override-engine`'s issue shape (the Rust equivalent of `runPhase4Checks`).
- **`override-engine`** — the issue/override model: stable ids, severity scoring, override validation.
- **`db-store`** — the SQLite layer (`ignite.db`). `repositories.rs` (US-01, see below) adds the durable `repositories`/`source_snapshots`/`scan_runs` identity model alongside the original `projects` table.
- **`config`** — `config.json`/env-var loading.
- **`tool-runner`** — every external-tool/`git`/`gh` subprocess invocation, with the same argument-array-only (no shell) sanitization the Node original had via `execFile`.
- **`github-api`** — shared `gh`-CLI-first/token-fallback GitHub operations (clone, PR create, commit status, etc.), used by the server's push path and by the standalone tools below.

## GHAS-bypass hardening (Rust-only, `rust/crates/`)

The pitch for dropping GitHub Advanced Security in favor of Ignite is only true if Ignite actually replaces what GHAS does automatically. Gaps closed so far:
- **`scheduled-rescan`** (`rust/crates/scheduled-rescan`): Dependabot-equivalent continuous coverage. Iterates every onboarded `(org, repo)` in `db-store`'s `projects` table, shallow-clones each one's current GitHub default branch, runs a real `POST /api/pipeline/validate-all` against a running Ignite server, and posts findings back via the existing `POST /api/pipeline/:jobId/github-check` path — only on a non-clean result; a clean scan just logs. HTTP client timeout defaults to 1800s (`IGNITE_SCHEDULED_RESCAN_TIMEOUT_SECS`), sized for real Phase 4 runs (5-16+ min per `rust/MIGRATION_STATUS.md`). Not wired into anything automatically — run by hand/cron/systemd, or a GitHub Actions `schedule:` trigger (example in `docs-site/docs/ci-integration.md`). Optionally chains straight into `auto-fix-pr` (below) on a non-clean result — see that entry for the opt-in env var.
- **`auto-fix-pr`** (`rust/crates/auto-fix-pr`, library crate `ignite-auto-fix-pr`): the Dependabot-parity gap `scheduled-rescan` itself leaves open — it detects a newly-disclosed CVE but never proposes the fix the way Dependabot's version-bump PRs do. Standalone CLI, dry-run by default (`--apply` to actually push/open PRs), same convention as `enforce-gate-branch-protection`. For each repo: shallow-clones the default branch, runs the real `dependency-vulnerability` scan (`ignite-dependency-license-scan`), resolves each finding's minimum fixed version via a real OSV.dev API call (deps.dev's own advisory schema, already used by that scan, has no per-package fixed-version field), and opens one PR per safe fix via `ignite-github-api`'s `gh_create_pr`. Deliberately conservative: only single simple version constraints are auto-edited (OR-ranges/wildcards/hyphen-ranges are left for a human), and a fix crossing a semver major version is always skipped, never silently applied. Idempotent via `git ls-remote --heads` on a deterministic per-(ecosystem, dependency, fixed-version) branch name.
  - **Auto-chained from `scheduled-rescan`**, opt-in via `IGNITE_SCHEDULED_RESCAN_AUTO_FIX` (unset/anything else = `off`, the default — an existing deployment's behavior never changes silently). `dry-run` discovers fix candidates and logs the plan without pushing; `apply` actually pushes branches and opens PRs. When enabled, `rescan_one` (`crates/scheduled-rescan/src/lib.rs`'s `run_auto_fix`) calls this crate's `discover_fix_candidates`/`apply_fix` directly against the checkout it already cloned for the rescan itself — no second clone — right after finding a non-empty issue list and before posting the commit status, so the commit status a human reads already reflects any fix PR just opened.
  - **Routine (non-vulnerability) dependency updates** (`--include-routine-updates`, CLI-only, opt-in — never auto-chained from `scheduled-rescan`): Dependabot's other half — `discover_routine_update_candidates` walks every manifest `ignite-studio-manifests` parses, resolves each dependency's current version (lockfile-pinned if present, else `best_effort_version` off the declared range), looks up the latest published version via `DepsDevClient::fetch_version_list`, and proposes a bump to the highest non-prerelease semver strictly newer than current — with no advisory driving it at all. Shares every mechanic with the vulnerability path (`FixCandidate.kind: FixKind`, `apply_fix`, lockfile regeneration, major-bump-always-skipped, per-(dep,version) branch idempotency); only PR title/body/commit-message wording differ (no advisory/OSV.dev references — `chore(...)` commit prefix instead of `fix(...)`).
  - **Gradle and NuGet ecosystem support**: alongside the original npm/pypi/cargo/go/maven, `ignite-studio-manifests` now parses `build.gradle`/`build.gradle.kts` (Groovy/Kotlin DSL string-notation deps only — map notation and version catalogs deliberately unsupported, same "leave the ambiguous case for a human" posture as OR-ranges) and `*.csproj` `PackageReference` elements (both attribute and nested-`<Version>` forms). `*.csproj` is the one manifest whose filename isn't fixed (`MyApp.csproj`), so `find_manifest_spec` matches a `"*.ext"` table entry by suffix instead of the exact-name equality every other entry uses. `lockfile_command` gained `dotnet restore --force-evaluate`/`gradle dependencies --write-locks` arms (gated on the lockfile already existing, like every other ecosystem); `FIXED_COMMANDS` gained `dotnet`/`gradle` so they're actually invokable.
  - **Dependabot `groups:` config parity** (`--group-by ecosystem`, CLI-only, opt-in — never auto-chained from `scheduled-rescan`, same posture as `--include-routine-updates`): without it, every fix candidate opens its own PR, which floods a stale/legacy repo with dozens of PRs on one run — the gap flagged against real Dependabot behavior. `group_candidates` (`rust/crates/auto-fix-pr/src/lib.rs`) partitions the flat candidate list into `(ecosystem, FixKind)` buckets — vulnerability fixes and routine chores are never bundled into the same PR even under grouping, since their commit-prefix/urgency genuinely differ. `apply_fix_group` is the multi-candidate counterpart to `apply_fix`: a singleton group is hand-delegated straight to `apply_fix` unchanged (byte-identical branch name/behavior to pre-grouping), so `--group-by` never alters output for a repo that only ever surfaces one candidate per ecosystem at a time. A real (2+ member) group gets one deterministic branch (`group_branch_name` — FNV-1a hash of the sorted `dep@version` set, so membership changes produce a new branch the same way `branch_name_for` does per-candidate), all its manifest edits applied onto one checkout before a single commit/push, and one PR (`pr_title_for_group`/`pr_body_for_group`, bullet-listing every bundled dependency). Per-member conservatism carries over unchanged: a major-bump candidate is excluded from its group (reported individually, never silently dropped), and a candidate whose manifest line no longer matches the scan is skipped without failing the rest of the group.
  - **`dependabot.yml` ignore-rule parity** (`rust/crates/auto-fix-pr/src/dependabot_config.rs`, on by default, no flag to disable): a dependency a team has already told real Dependabot never to touch (`.github/dependabot.yml`'s `ignore:` list, matched by ecosystem + Dependabot's own `dependency-name` glob syntax) is now respected by both `discover_fix_candidates` and `discover_routine_update_candidates` too, instead of Ignite silently proposing a fix Dependabot itself was configured to skip. Deliberately narrow: `directory:`-scoped monorepo targeting needs no separate handling (`ignite_fs_utils::walk_files` already recurses the whole repo tree regardless), and `versions:`-scoped ignore rules aren't range-matched — naming any version still suppresses the dependency entirely, over-suppression being the safe failure direction. Schedule/target-branch/private-registry-credentials are out of scope; credentials in particular need real secret storage, a separate and more careful feature.
- **`enforce-gate-branch-protection`** (`rust/crates/enforce-gate-branch-protection`): standalone CLI, dry-run by default (`--apply` to actually change anything), that requires the `ignite/gate` status check and blocks direct/admin-bypass pushes on a repo's default branch via `gh api` (argument arrays, no shell). Not wired into any pipeline path by default — an operator runs it deliberately, though `routes/repository_events_webhook.rs` (below) can now call its org-ruleset half automatically. Split into `lib.rs` (all the actual logic, `pub`) + a thin `main.rs` CLI wrapper so the webhook can call `plan_for_org`/`apply_org_plan` as a library instead of shelling out to the binary — behavior/tests unchanged by the split.
- **CodeQL query-suite pinning** (`config.example.json`'s `security.codeql.querySuites`): pinned to explicit query-pack versions instead of an unpinned `security-extended` reference — dropping GHAS means losing GitHub's continuously-updated CodeQL packs, so the ruleset is static until a human re-pins it. `reviewCadenceDays`/`lastReviewedAt` drive a non-blocking server-startup warning (`ignite-config::is_codeql_review_overdue`) when the pin is unset or stale.
- **Doc-only note**: even when dropping the rest of GHAS, keep GitHub's basic secret-scanning push-protection on — it's the one pre-receive capability Ignite's post-hoc scan structurally can't replace (a secret pushed then deleted in a follow-up commit was still exposed in the window between). Flagged as something to verify against the real GitHub bill, not a settled pricing fact. See `docs-site/docs/ci-integration.md`.
- **Native GitHub UI parity (SARIF + Dependency graph)**: findings/dependency data previously lived only in Ignite's own UI — GHAS surfaces both in GitHub's own Security/Insights tabs. `rust/crates/github-api`'s `gh_upload_sarif` (`POST repos/{full}/code-scanning/sarifs`, gzip+base64 per GitHub's API contract) and `gh_submit_dependency_snapshot` (`PUT repos/{full}/dependency-graph/snapshots`, GitHub's Dependency Submission API schema) push to those tabs. Both are wired into `POST /api/pipeline/:jobId/github-check` (`rust/crates/server/src/routes/github_pr_status.rs`) — the same call a pre-push hook/CI already makes to post the `ignite/gate` commit status, since that's the one place `(owner, repo, sha)` are already validated together against a commit guaranteed to exist on GitHub. The SARIF doc reuses `ignite-sarif::build_sarif` against the job's issues; the dependency snapshot reuses `ignite-dependency-license-scan::build_dependency_graph_snapshot` against `DbStore::get_dependency_scan_cache`'s cached scan (no second scan). `ref` is an optional field on the `github-check` request body — falls back to the repo's current default branch when omitted. Both pushes are best-effort/non-fatal (logged via `tracing::warn!`, never fail the gate-status response) and independently toggleable: `security.codeScanning.enabled` / `security.dependencyGraph.enabled` in `config.json` (`CODE_SCANNING_ENABLED`/`DEPENDENCY_GRAPH_ENABLED` env overrides), both on by default.
- **Git-history secret scan**: `ignite-secrets`'s built-in scan and its optional gitleaks supplement both only ever walked the current working tree — a secret committed then removed in a later commit stayed invisible, the one gap GHAS's own secret-scanning alerts (as opposed to push-protection) exist to catch. `run_gitleaks_history_scan` (`rust/crates/secrets/src/lib.rs`) runs `gitleaks detect` against full commit history (omitting `--no-git`, unlike the working-tree-only `run_gitleaks_scan`) — a no-op returning no findings when `root/.git` doesn't exist (an uploaded ZIP with no git history). Findings are tagged with a distinct tool name (`merge_gitleaks_history_findings` → `"gitleaks-history"`, vs. `"gitleaks"` for the working-tree run) and deduped against working-tree findings at the same file:line so a still-present secret isn't reported twice. Independent of `security.gitleaks.enabled`'s own working-tree gitleaks run: `security.gitleaks.scanHistory` in `config.json` (`GITLEAKS_SCAN_HISTORY` env override), default `false` — but `phase4-orchestrator::run_phase4_checks` (`rust/crates/phase4-orchestrator/src/lib.rs`) forces this on regardless of the config value whenever the run isn't in `fast` mode, since full runs (the default for the headless/pre-push/scheduled-rescan path) are exactly the case where the extra time is acceptable. The config default only actually matters for `fast` mode, which never runs it. `security.trivyImage.enabled` (the container-image `trivy image` scan, off by default for the same cost reason) is a deliberate *exception* to this pattern: unlike the git-history scan, a real `docker build` per Dockerfile plus a full `trivy image` scan can run into several minutes per image, so `phase4-orchestrator` honors the config value as written even in full mode rather than forcing it on — an operator opts into the extra GHAS-parity coverage explicitly (`TRIVY_IMAGE_ENABLED=true`) instead of it silently making every full run slow by default.
- **Private vulnerability reporting** (`rust/crates/report-vulnerability`, bin `report-vulnerability`): GHAS lets a maintainer privately draft a Security Advisory to coordinate a fix before public disclosure — Ignite's own `auto-fix-pr` (above) does the opposite by design, going straight to a public fix PR, so it can't cover this. Standalone CLI, same dry-run-by-default/`--apply` convention and `gh api ... --input <tmpfile>` mechanics as `enforce-gate-branch-protection` (nested JSON body, no shell). `report-vulnerability <org/repo> --summary <str> --severity <critical|high|medium|low> --ecosystem <eco> --package <name> --vulnerable-range <range> [--patched <version>] [--description <str>] [--cwe <id>]... [--apply]` creates a draft advisory via `POST repos/{full}/security-advisories`. Deliberately never wired into any scan/pipeline path — opening a private advisory is a judgment call about whether a finding needs private coordination at all, not something a scan should decide unattended. Three more subcommands complete the private-coordination workflow around a draft advisory, each taking `<org/repo> --ghsa-id <id>` (the id the create command printed/returned), same dry-run-by-default/`--apply` posture: `report-vulnerability fork <org/repo> --ghsa-id <id> [--apply]` creates a **temporary private fork** (`POST .../security-advisories/{ghsa_id}/forks`) for collaborators to push a fix to without it being visible anywhere public; `report-vulnerability request-cve <org/repo> --ghsa-id <id> [--apply]` requests a CVE identifier for the draft (`POST .../security-advisories/{ghsa_id}/cve`); `report-vulnerability publish <org/repo> --ghsa-id <id> [--apply]` transitions the advisory `draft` → `published` (`PATCH .../security-advisories/{ghsa_id}`, `{"state": "published"}`) — **the one irreversible action** in this tool, since everything else only ever creates/mutates something still private. `parse_top_level_args` dispatches on the first CLI argument being one of `fork`/`request-cve`/`publish`; anything else (including every pre-existing invocation) falls through to the original create-advisory form unchanged, so this is purely additive.
- **GitHub Actions workflow security (zizmor)** — added after `ignite-guidelines`' narrow `no-unpinned-gha-action` regex check was found to only cover mutable-ref pinning, not the actually dangerous GHA classes (pwn requests, script injection, over-broad `permissions:`). Crate `rust/crates/gha-security` (`check_gha_security`, `GhaSecurityConfig`) wired into `phase4-orchestrator`'s concurrent fan-out; skips invoking `zizmor` entirely when a repo has no `.github/workflows/*.yml`. Config: `security.zizmor.{enabled,binary}` (`ZIZMOR_ENABLED`/`ZIZMOR_BINARY`), on by default. Issue category `gha-security` (CWE-829, OWASP A08:2021) in `override-engine`. No built-in fallback — needs zizmor's real workflow-expression parser.
- **Dependabot-style lockfile regeneration in `auto-fix-pr`**: a manifest-only version bump (the tool's original behavior) fails CI on any repo that enforces a matching lockfile — `regenerate_lockfile`/`lockfile_command` (`rust/crates/auto-fix-pr/src/lib.rs`) detect the ecosystem's lockfile next to the manifest (`package-lock.json`/`yarn.lock`/`pnpm-lock.yaml`, `Cargo.lock`, `go.sum`) and run the matching package-manager command (`npm install --package-lock-only`, `yarn install --mode update-lockfile`, `pnpm install --lockfile-only`, `cargo update -p <dep> --precise <version>`, `go mod tidy`) before committing, staging the lockfile alongside the manifest edit. `requirements.txt`/pypi and `pom.xml`/maven have no separate lockfile step (the manifest already is the pinned file, or there's no lock concept), so nothing runs for those. Best-effort: a failure (missing binary, network, resolution conflict) is folded into a warning in the commit message and PR body rather than failing the whole fix — `git`/`gh`/`npm`/`yarn`/`pnpm`/`cargo`/`go`/`poetry`/`pip-compile` are all in `tool-runner`'s `FIXED_COMMANDS` allowlist, resolved directly off `PATH`.
- **PR "Dependency Review" sticky comment**: GHAS-parity for `dependency-review-action`'s PR summary — `rust/crates/dependency-license-scan/src/dependency_diff.rs`'s `diff_dependency_scans`/`render_dependency_diff_comment` diff two cached `scan_json` snapshots (added/removed/version-changed/license-changed dependencies, rendered as collapsible markdown with tier badges) and post/update a single marker-tagged comment via `ignite-github-api`'s `gh_upsert_pr_sticky_comment` (lists existing PR comments, edits the one carrying `DEPENDENCY_REVIEW_MARKER` in place instead of accumulating one per push). Wired into `github_pr_status.rs`'s `github_check` handler alongside the SARIF/dependency-graph pushes — best-effort/non-fatal, only fires when `prNumber` is given. **Baseline caveat**: diffs against this project's own *previous* cached scan (`DbStore::get_previous_dependency_scan_cache`, populated by `save_dependency_scan_cache` shifting the old value on each overwrite), not a second clone-and-rescan of the PR's actual base branch — correct for the common case (a PR based on the org/repo's own last-scanned default branch), but can include unrelated changes when it isn't (see the module's own doc). Config: `security.dependencyReview.enabled` (`DEPENDENCY_REVIEW_ENABLED`), on by default.
- **Active secret verification, multi-cloud** (`rust/crates/secret-verifier`, off by default): GHAS's secret-scanning partner program pings the issuing provider to tell a live leaked token apart from a dead/test one — `verify_secret`/`extract_secret_value` do the same for GitHub (`GET /user`), Slack (`auth.test`), Stripe (`GET /v1/balance`), and GCP API keys (`GET translation.googleapis.com/language/translate/v2?key=...`, classified off Google's documented "API key not valid" rejection message vs. any other error, which proves the key itself cleared auth), matched off the finding's `kind` (gitleaks' own rule id) and the raw token pulled out of the finding's code snippet via the same publicly-documented token-format regexes gitleaks itself keys detection on. **AWS** (`sts:GetCallerIdentity`) is also implemented — a real SigV4 signing implementation (`sign_get_caller_identity`, canonical-request → string-to-sign → `AWS4<secret>→date→region→service→"aws4_request"` HMAC-SHA256 signing-key chain, per AWS's own documented algorithm), needed since unlike the bearer-token providers AWS requires both credential halves (access key id *and* secret access key) signed together — `extract_aws_credential_pair`/`verify_secret_pair` is a separate pair-based path from the single-string one, matched over the finding's *full* multi-line snippet (not just the highlighted line) since the two halves commonly sit a line or two apart. `us-east-1` is hardcoded (STS's global endpoint answers for a credential from any region); a 403 (`InvalidClientTokenId`/`SignatureDoesNotMatch`) is `Revoked`. Empirically verified against the real AWS/Google APIs in this crate's own tests (self-skipping the same way the GitHub test does if network is unavailable) — both the rejection path for a syntactically-valid-but-fake credential were confirmed against the live provider network while building this. **Azure is still deliberately unimplemented** — unlike AWS's/GCP's single well-known global hostnames, Azure Storage account keys sign a request against a *per-customer* `{account}.blob.core.windows.net` subdomain that only resolves for a real existing account, so there's no way to empirically verify a Shared-Key-signing implementation against the real network without one, and a subtly wrong canonicalization risks misclassifying a genuinely live credential as revoked rather than failing safe into `Unknown`. Every check is read-only/non-destructive and never logs the raw value. Wired into `phase4-orchestrator::run_phase4_checks`: when enabled, a `Live` result appends `" — VERIFIED LIVE"` to the finding's `kind`; disabled (the default), nothing changes and no network call happens. Config: `security.secretVerification.{enabled,timeoutMs}` (`SECRET_VERIFICATION_ENABLED`), `enabled` defaults to `false` — sending a credential found in scanned code to a third-party API is an operator's explicit call to make, not a default a static-analysis check should opt into silently. **OpenAI** (`GET /v1/models`, bearer), **Anthropic** (`GET /v1/models`, `x-api-key`+`anthropic-version` headers — not bearer, per Anthropic's own API contract), **npm** (`GET /-/npm/v1/user`, bearer), and **Datadog** (`GET /api/v1/validate` — Datadog's own purpose-built key-check endpoint, not a repurposed unrelated read like every other provider here) are also implemented, same read-only/never-logs-the-value/best-effort posture, all four "revoked" paths empirically verified against the real live provider APIs while building this. **PyPI is deliberately still unsupported**, for a different reason than Azure: it has no read-only "check this token" endpoint at all, only the actual package-upload endpoint — a write path unsafe to probe.
- **Code-scanning alert-dismissal sync**: previously one-directional — `gh_upload_sarif` creates GitHub Code Scanning alerts, but overriding the same finding in Ignite never touched GitHub's copy, so a justified/overridden issue kept showing as an open alert in GitHub's own Security tab. `find_matching_open_alert_number` (`rust/crates/server/src/routes/github_pr_status.rs`) matches an already-`"overridden"` `IssueRow` against `GithubApi::gh_list_code_scanning_alerts`' response by `rule.id` (the same `ignite_sarif::rule_id_for` mapping the SARIF upload used) plus the alert's most recent instance's file/line — GitHub's alerts API doesn't echo back SARIF's `partialFingerprints`, so this is the same file:line matching convention used elsewhere in this codebase (gitleaks/built-in dedup, override fuzzy-match). A match gets dismissed via `GithubApi::gh_dismiss_code_scanning_alert` (`dismissed_reason: "won't fix"`, `dismissed_comment` carrying Ignite's actual justification text). Runs right after the SARIF upload in `github_check`'s existing `code_scanning.enabled` block; best-effort/non-fatal like every other push there. Config: `security.codeScanning.syncDismissals` (`CODE_SCANNING_SYNC_DISMISSALS`), on by default whenever `codeScanning.enabled` is — only ever dismisses alerts backing an override Ignite itself already recorded, never based on unattended scan output. The GitHub→Ignite direction is now implemented too — see the next bullet.
- **Inbound code-scanning alert-dismissal sync (GitHub → Ignite)**: closes the direction the bullet above left open — a human dismissing or reopening a code-scanning alert directly in GitHub's **Security** UI previously never reached `ignite.db`, so the next `validate-all`/gate check kept treating the finding as an unapproved open issue. `POST /api/webhooks/github/code-scanning` (`rust/crates/server/src/routes/code_scanning_webhook.rs`) receives GitHub's `code_scanning_alert` webhook, verifies `X-Hub-Signature-256` (HMAC-SHA256) against `security.codeScanning.inboundWebhookSecret` (`CODE_SCANNING_INBOUND_WEBHOOK_SECRET`, unset by default — the endpoint 404s until a secret is configured, so an unconfigured deployment never exposes an unauthenticated write path), and maps the alert back to an Ignite issue with the same rule-id + file + line match `find_matching_open_alert_number` uses in the outbound direction. A `dismissed` delivery inserts an `overrides` row (`actor_email` sentinel `db_store::GITHUB_DISMISSAL_ACTOR_EMAIL`, justification drawn from GitHub's own dismissal reason/comment) via the existing `add_override`, then immediately flips that project's `issues.status` to `overridden` (`DbStore::set_issue_status`) rather than waiting for the next scan — and because `get_carry_forward_overrides` already reads across every past project of a repo, the same dismissal survives into the next real scan for free, no new carry-forward path needed. A `reopened` delivery removes exactly the override rows the webhook itself created (`DbStore::delete_github_dismissal_overrides`, scoped by the actor-email sentinel so a real human-justified Ignite override on the same issue id is never touched) and flips the issue back to `open` only if no other override still covers it (`DbStore::issue_has_override`). Not wired through `RequireAuth` — GitHub's webhook delivery has no Ignite session/API key; the HMAC check is the endpoint's only auth. Both directions emit an `audit-log` event (`code_scanning_alert.dismissed_on_github` / `.reopened_on_github`).
- **Push-protection bypass webhook/remediation**: GitHub's own secret push-protection can block a commit at pre-receive time, but a developer is still allowed to push anyway after giving a justification — GitHub can notify the org of that bypass via a `secret_scanning_alert` webhook carrying `push_protection_bypassed: true`, previously unseen by Ignite entirely. `POST /api/webhooks/github/push-protection` (`rust/crates/server/src/routes/push_protection_webhook.rs`) receives it — same `X-Hub-Signature-256` HMAC-verification/404-until-configured posture as the code-scanning webhook above, via `security.pushProtection.inboundWebhookSecret` (`PUSH_PROTECTION_INBOUND_WEBHOOK_SECRET`). Every delivery that isn't a bypass (`extract_bypass_info` returns `None`) is acknowledged and ignored — every other `secret_scanning_alert` action is the inbound secret-scanning webhook's concern (next bullet). A real bypass always emits a `critical`-severity `push_protection.bypassed` audit-log event (actor, secret type, stated reason/comment, alert URL) so a SIEM sink sees it regardless of anything else; `security.pushProtection.autoFileIssue` (off by default — reaching out unattended is an operator's explicit call, same posture as `secretVerification`) additionally files a real GitHub issue via `gh_create_issue` summarizing the bypass, so it lands somewhere a human is already looking instead of only a log line. Both best-effort/non-fatal.
- **Inbound secret-scanning alert lifecycle sync**: the push-protection webhook above only ever looks at the `push_protection_bypassed: true` case of a `secret_scanning_alert` delivery — every other action (`created`, `resolved`, `reopened`, `validated`, `publicly_leaked`) previously reached nothing in Ignite. `POST /api/webhooks/github/secret-scanning` (`rust/crates/server/src/routes/secret_scanning_webhook.rs`, `SECRET_SCANNING_INBOUND_WEBHOOK_SECRET`) closes that gap. `resolved`/`reopened` mirror the inbound code-scanning webhook's own dismissal sync (`add_override`/`set_issue_status`/`delete_github_dismissal_overrides`), but matching needs one extra step the code-scanning payload doesn't: `secret_scanning_alert` carries no file/line at all, so `fetch_first_location` makes one `GET .../secret-scanning/alerts/{number}/locations` call (using whatever server-side GitHub token is configured) before matching on `category == "secret"` + file/line — a missing token or failed lookup degrades to "no matching issue" rather than failing the webhook. `created`/`validated`/`publicly_leaked` have no Ignite issue-state equivalent and are audit-log-only, `publicly_leaked` always at `critical`.
- **Zero-touch repo onboarding**: GitHub's org-level "Security Configurations" apply automatically to any new repo — Ignite previously had no equivalent, so a newly-created repo sat unprotected and unknown to Ignite until someone manually scanned it or ran `enforce-gate-branch-protection`/`scheduled-rescan` against it by name. `POST /api/webhooks/github/repository-events` (`rust/crates/server/src/routes/repository_events_webhook.rs`, `REPOSITORY_EVENTS_INBOUND_WEBHOOK_SECRET`) listens for `repository.created`/`.transferred` and always enrolls a minimal `projects` row immediately. Two further steps are independently opt-in (both off by default): `security.repositoryEvents.applyOrgRuleset` calls `enforce-gate-branch-protection`'s own `plan_for_org`/`apply_org_plan` as a library (not a subprocess); `security.repositoryEvents.triggerBaselineScan` spawns a background `ignite_scheduled_rescan::rescan_one` run against the new repo, fire-and-forget since a real scan can take minutes.
- **Dual-custody approval for critical-severity overrides**: previously any authenticated (or even just self-declared-in-the-body) user could submit an override and it took effect immediately regardless of severity — no role tiers exist anywhere in `auth`/`db-store` (confirmed; there's no `users.role` column or equivalent). `security.overrideApproval` (off by default) changes that for issues scoring `>= ignite_override_engine::CRITICAL_SCORE_THRESHOLD` (9, the same "critical" bucket the SLA-aging code already uses): the override is inserted `pending` (`DbStore::add_pending_override`) instead of taking effect, and the issue keeps blocking the gate, until a *different* user whose email is on the configured `approverEmails` allowlist calls `POST /api/projects/:id/overrides/:overrideId/approve` (`rust/crates/server/src/routes/override_approval.rs`) — a config-driven allowlist standing in for a real role/permission system, deliberately, rather than a much bigger schema/UI change. `ignite_override_engine::partition_for_dual_custody` is the one pure function both submission sites (`routes/effectivate.rs`, `routes/pipeline_interactive/run.rs`'s review gate) share to decide what needs a second reviewer; carried-forward/AI-assist auto-resolutions are unaffected since dual-custody is specifically about a human submitting a brand-new override right now.
- **Inline PR review suggestions (Copilot Autofix parity)**: GHAS's Copilot Autofix posts inline PR review comments carrying a ```suggestion fenced block, which GitHub's diff viewer renders with a one-click "Commit suggestion" button — Ignite previously only offered leaving the PR entirely for a bulk fix-PR (`crates/fix-pr`) or a standalone `auto-fix-pr` run. `ignite_fix_pr::build_pr_suggestions` (`rust/crates/fix-pr/src/lib.rs`) turns a batch of `FixCandidate`s into one `PrSuggestion` per single-line edit (`start_line == end_line`) — deliberately narrower than the rest of fix-pr: it reuses the exact same conservative category set `SINGLE_LINE_FIX_CATEGORIES` (currently just `dependency-vulnerability`) that `narrow_snippet_for_edit` already restricts to one editable line, so nothing here ever proposes a suggestion wider than what `auto-fix-pr` already trusts itself to mechanically apply unattended. Wired into `github_check` (`rust/crates/server/src/routes/github_pr_status.rs`) alongside the SARIF/dependency-graph/dependency-review pushes, only when a PR number is present: filters the job's still-open issues to that category set, runs them through fix-pr's own `generate_fix_candidates` (no reimplementation of the LLM fix-computation), and posts each single-line result via `ignite_github_api::gh_create_pr_review_comment` (`POST repos/{full}/pulls/{pr}/comments`, GitHub's PR Review Comments API — `commit_id`/`path`/`line`/`side: "RIGHT"`). **Dedupe**: the Review Comments API has no PATCH-based upsert (unlike `gh_upsert_pr_sticky_comment`'s marker-edit trick for issue comments), so each suggestion's body carries a hidden `<!-- ignite:suggestion:<issue_id> --> ` marker and `gh_list_pr_review_comments` + `find_review_comment_marker` are checked first — an issue whose marker is already present on the PR is skipped outright rather than posted again on every push. Best-effort/non-fatal like every other push in `github_check`. Config: `security.prSuggestions.enabled` (`PR_SUGGESTIONS_ENABLED`), on by default — safe precisely because the scope is this narrow, same posture as `dependencyReview`. **Multi-line suggestions** are now also supported for `semantic-sast` findings (`ignite_fix_pr::MULTI_LINE_SUGGESTION_CATEGORIES`, semgrep/bearer-family taint/semantic issues) — `build_pr_suggestions` keeps a multi-line candidate only when its `original`/`replacement` share the same bracket-depth signature (the same structural safety net bulk-fix apply already uses before writing to disk), and `GithubApi::gh_create_pr_review_comment_range` adds GitHub's `start_line`/`start_side` fields for the multi-line case; `SINGLE_LINE_FIX_CATEGORIES` stays single-line-only, unchanged.
- **Org-wide GitHub Ruleset enforcement**: `enforce-gate-branch-protection`'s original per-repo classic branch protection only protects a repo once someone remembers to run the tool against it by name — a newly-created repo in the org has no protection until then. `--org <org-name>` (repeatable, freely mixable with `<org/repo>` targets in one invocation) instead creates/updates an org-wide GitHub Repository Ruleset (`POST`/`PUT orgs/{org}/rulesets`, GitHub's newer API that applies to every current *and future* repo in the org) requiring the `ignite/gate` status check on each repo's default branch, blocking force-pushes/branch deletion, and requiring one reviewed PR — `bypass_actors: []` is the ruleset equivalent of `enforce_admins: true`, no one bypasses it. `find_existing_org_ruleset_id` looks up a ruleset already named `ignite-gate` first (`GET orgs/{org}/rulesets`) so a repeat run updates that ruleset in place (`PUT .../rulesets/{id}`) instead of creating a duplicate on every invocation. Same dry-run-by-default/`--apply` convention as the per-repo path; the org-ruleset payload's nested JSON goes through `GithubApi::gh_api_write`, which already detects a non-scalar field and routes through the raw REST fallback instead of mangling it through `gh api -f`.
- **Org ruleset drift detection/reconciliation**: the org-ruleset flow above only guarantees policy *at the moment it's applied* — an org-admin can still loosen the ruleset by hand afterwards (drop `ignite/gate`, add a bypass actor, delete a rule) directly in GitHub's UI, and the one-shot CLI has no way to notice until someone happens to re-run it. `--org <org-name>... --check-drift [--apply]` (`rust/crates/enforce-gate-branch-protection/src/main.rs`) turns it into a continuous check: fetches each target org's *current* ruleset (`GET orgs/{org}/rulesets/{id}`) and diffs it against the policy via `detect_ruleset_drift` — a pure function that checks the specific fields the policy cares about (enforcement, empty bypass_actors, and each of the four required rule types/parameters) rather than a byte-for-byte comparison, since GitHub's API echoes back extra server-assigned fields (`id`, `created_at`, per-rule ids) that would make an exact diff report drift on every call. Report-only by default (never mutates); pair with `--apply` to also reconcile (re-`PUT` the correct ruleset) whatever's drifted. Exit code is the signal a cron/CI caller watches: `0` clean, `2` drift found (even if `--apply` just fixed it — the caller wants to know drift *happened* this run), `1` on a lookup/apply error. Not wired into any scheduled path itself, same posture as the rest of this tool — run it from cron/a scheduled GitHub Actions workflow.
- **Custom secret patterns: playground + retroactive sweeper** (GHAS custom-pattern parity, `POST`/`GET /api/secret-patterns`): `ignite_secrets::test_pattern_against_sample` is the "playground" — compiles an operator-supplied regex and runs it against sample text, returning every match's position/text, so a pattern can be tried out before it's saved. No auth, no persistence (same posture as `routes/campaigns.rs`); Rust's `regex` crate's linear-time guarantee (no catastrophic backtracking, unlike PCRE behind GHAS's own editor) is why this is safe to run synchronously against arbitrary input — length/match-count caps exist for sane responses, not ReDoS. Saved patterns live in `db-store`'s `custom_secret_patterns` table (name/regex/enabled). `POST /api/secret-patterns/:id/sweep` is the retroactive half — GHAS custom patterns can check whether they'd have caught something already committed; `ignite_secrets::build_gitleaks_config_for_patterns` turns a pattern into a throwaway gitleaks TOML rule (`[extend] useDefault = true` keeps gitleaks' own built-ins active alongside it; the regex goes in a TOML literal string so it needs no escaping), and the sweep clones the target repo with full history (`GithubApi::gh_clone_repo_branch_full_history` — unlike every other clone site in this codebase, a shallow `--depth 1` clone would defeat the point) before running the existing `run_gitleaks_history_scan` against it. Requires auth (clones a real repo, spends a GitHub token) — same posture as `fix_pr.rs`'s `apply`. **Live-scan wiring**: every `enabled` pattern also applies to the regular working-tree/history scan, not just the playground/sweep. `phase4-orchestrator::run_phase4_checks` calls `store.list_enabled_custom_secret_patterns()` and, when non-empty, builds a merged config via `build_gitleaks_config_for_patterns(patterns, config.secrets.gitleaks_config_path.as_deref())` — extending the operator's own `gitleaks_config_path` (when one is set) rather than gitleaks' stock defaults, so a deployment's existing tuned config isn't silently dropped. The merged TOML is written as a job-UUID-named sibling of the staging root (never inside it, so it isn't itself scanned as source) and removed after both gitleaks calls complete. A disabled pattern is excluded by the `WHERE enabled = 1` query itself, never filtered client-side.
- **Transitive dependency reachability**: a `dependency-vulnerability` finding today gates a push identically whether the vulnerable package is genuinely wired into the project or just an unused transitive dependency sitting in the lockfile — a real gap against tools that factor reachability into urgency. Full call-graph reachability (a real per-language parser/type-checker resolving every call site) is its own multi-week initiative; what's here is the honest, defensible slice of it achievable with lightweight regex-based source scanning, covering 4 of 5 ecosystems this codebase already resolves dependency vulnerabilities for. Every layer below is **deliberately annotation-only** — severity/score are never touched, this is a human-facing triage signal, not something a scan should decide unattended:
  - **npm, import-level**: `ignite_module_graph::collect_imported_packages` (`rust/crates/module-graph/src/lib.rs`) aggregates every file's already-parsed `bare_imports` (from `build_module_graph`, shared with the dead-code/boundaries checks) into one project-wide set of root npm package names — `root_package_name` normalizes a scoped subpath import (`@org/pkg/dist/thing`) or unscoped subpath (`lodash/get`) down to the package a `package.json` would actually list. Appends `[not directly imported in project source]` when the flagged package isn't in that set.
  - **Go, function-level** (`rust/crates/dependency-license-scan/src/reachability.rs`): strictly more precise than import-level, because Go's own vulndb — uniquely confirmed among the ecosystems checked — populates OSV's `affected[].ecosystem_specific.imports[].{path,symbols}` with the *exact vulnerable function names*; confirmed empirically against both the live `api.deps.dev` and `api.osv.dev` APIs while building this (deps.dev's own advisory mirror silently strips the field; raw osv.dev has it). `DepsDevClient::fetch_osv_record` (`rust/crates/deps-dev-client/src/lib.rs`) fetches the raw OSV record directly (bypassing deps.dev's stripped `/v3/advisories` mirror) only for `go`-ecosystem findings; `extract_go_affected_imports` pulls out the Go-specific symbol data. `scan_go_project` walks/parses every `.go` file's imports exactly once per scan (not once per finding — a project with several distinct Go advisories carrying symbol data would otherwise re-walk the same files repeatedly); `check_go_reachability` then checks whether any named vulnerable symbol is actually *called* (`alias.Symbol(`, alias/blank `_`/dot `.` imports all handled) against that cached parse — not just whether the package is imported — appending `[vulnerable function(s) not called: X, Y]` when none is. Falls back to no annotation at all when the advisory carries no symbol data (the common case, even for Go).
  - **Python (pypi), import-level** (`rust/crates/dependency-license-scan/src/python_imports.rs`): `collect_python_imported_modules` regex-scans every `.py` file for `import x`/`from x import y` (top-level module name only; relative imports — `from . import x` — never match, same relative-vs-bare distinction as npm/Go). The pip-package-name-vs-import-name mismatch npm/Go don't have (`PyYAML` imports as `yaml`, `beautifulsoup4` as `bs4`, `Pillow` as `PIL`, ...) is handled by `expected_python_import_name`'s `PIP_NAME_ALIASES` table for well-known unambiguous cases, falling back to PEP 503 normalization (lowercase, hyphens/dots to underscores) otherwise — deliberately excludes ambiguous multi-package-shared-namespace cases like `protobuf` (imports under the `google` namespace shared by dozens of unrelated `google-*` packages) rather than risk a misleading match. Confirmed empirically against a real pypi/GHSA advisory (Starlette's GHSA-82w8-qh3p-5jfq) that pypi carries no OSV symbol-level data — function-level reachability isn't possible here the way it is for Go.
  - **Rust (cargo), import-level** (`rust/crates/dependency-license-scan/src/cargo_imports.rs`): `collect_used_rust_crates` scans for *any* `crate_name::` path prefix anywhere in `.rs` source, not just `use` declarations — idiomatic Rust routinely calls a dependency through a fully-qualified path with no `use` at all (`rand::random()`, `serde_json::to_string(&v)`), so scanning only imports (this crate's own convention for every other ecosystem) would miss the common case; `use foo::bar;` already contains the same `foo::` substring a bare `foo::bar()` call would, so one pass covers both. `expected_rust_module_name` converts a crate's hyphens to underscores (`tokio-util` -> `tokio_util`), the one normalization Cargo enforces unconditionally for every published crate — no alias table needed, unlike Python's.
  - **Rust (cargo) function-level — evaluated, deliberately not implemented**: RustSec advisories *do* carry symbol-level data via OSV's `affects.functions` (confirmed empirically, e.g. RUSTSEC-2021-0130 names `lru::LruCache::iter`/`lru::LruCache::iter_mut` exactly) — but unlike Go's affected symbols, which are always free functions called with an explicit package-qualified prefix in real code, RustSec's are frequently *methods on a type*, and real Rust code calls a method as `my_cache.iter()` with no textual reference to `LruCache` at the call site at all. A regex scanner has no way to resolve `my_cache`'s type without real type inference, so attempting this would systematically mislabel a used method as unreachable — a correctness trap worse than not having the signal, not merely an incomplete one. Left unimplemented for the same reason AWS SigV4 was originally deferred: don't ship a check that can't be verified correct.
  - **Java (maven) — deliberately not implemented**: unlike npm/pip/cargo, Maven's artifactId has no reliable mapping to the Java package name it's actually imported under (`commons-io` imports as `org.apache.commons.io`; `guava` as `com.google.common`) — no PEP-503-style normalization rule exists to fall back on the way it does for Python, so a name-guessing table would only ever cover a small, arbitrary slice of the real Maven ecosystem and produce real false "not imported" annotations for everything outside it. Same posture as the Cargo function-level and Azure (Gap 5) deferrals: a known, evaluated limitation, not a silently-skipped one.
- **Compliance audit packs** (`GET /api/compliance/audit-pack?from=YYYY-MM-DD&to=YYYY-MM-DD`, defaults to the trailing 90 days): SOC2/ISO27001-style evidence export — pure aggregation over data already collected for other features (`overrides`, `issue_first_seen`, `campaigns`), no new detection logic. `DbStore::list_overrides_in_range`/`mttr_by_severity_in_range` (`rust/crates/db-store/src/compliance.rs`) join `overrides` (who justified what, when, why — the change-management audit trail itself) against `issue_first_seen` (the same table `SlaConfig`'s breach math already reads) via SQLite `julianday()` arithmetic, the same pattern `sla.rs` already uses; an override whose `issue_first_seen` row has since aged out contributes to the count but not the avg/min/max (`NULL`, same as SQL's own aggregates ignoring it). The response bundles: overrides in the window (row-level evidence), MTTR-by-severity (explicitly labeled as time-to-formal-risk-acceptance, not time-to-fix — Ignite doesn't record a separate fixed-without-override timestamp), a live SLA-breach snapshot (`list_onboarded_repo_summaries`, not itself windowed — a point-in-time count is normal for this kind of control evidence), and campaign burndown (`list_campaigns`, as-is). API-only; see **Security campaigns** below for the UI that now exists for both features.
- **SLA tracking & overdue-issue enforcement** (`ignite_config::SlaConfig`, on by default): GHAS-parity vuln-management SLA — an open issue that just sits unresolved is real risk regardless of whether a new scan ever re-flags it. `issue_first_seen` (`rust/crates/db-store/src/schema.rs`) records a per-`(org, repo, issue_id)` "first ever detected" timestamp, upserted/pruned every `replace_project_issues` call (`rust/crates/db-store/src/issues.rs`) — an issue that disappears (fixed/no-longer-open) and later reappears gets a fresh timestamp, not a stale one. Bucketed by `override-engine`'s existing 0-10 issue score (>=9 critical, >=7 high, else medium) against `sla.{criticalDays,highDays,mediumDays}` (`SLA_CRITICAL_DAYS`/`SLA_HIGH_DAYS`/`SLA_MEDIUM_DAYS`, defaults 7/30/90). `DbStore::list_onboarded_repo_summaries` surfaces a `slaBreaches` count per repo (rendered as a badge in `public/index.html`'s Onboarded Repos table); `DbStore::{count,list}_sla_breaches` give the same for one project. `scheduled-rescan` fails the sweep (`find_sla_breaches` in `rust/crates/scheduled-rescan/src/lib.rs`, reusing `GET /api/onboarded-repos` rather than a new endpoint) whenever any repo has an SLA breach, even on a run whose own scan came back clean — the finding isn't new, it just aged past its deadline.
- **Security campaigns** (`rust/crates/db-store/src/campaigns.rs`, `POST`/`GET /api/campaigns`, `POST /api/campaigns/:id/close`): a named, org-wide "burn down every open issue matching this filter (category + minimum score) by this date" tracker. `create_campaign` snapshots `initial_open_count` (every onboarded repo's latest scan, matching the filter) at creation time; `list_campaigns` recomputes the live matching count on every call, so `resolved_count = initial_open_count - <live count>` (clamped at 0) never drifts out of sync with overrides/fixes landing after the campaign was created — no separate progress-tracking write path to keep in sync. Now has a UI: `public/index.html`'s Governance nav-rail view (Campaigns/Compliance tabs) lists campaigns with a live progress bar, a "New campaign" modal, and a Close action per row, plus a Compliance tab that generates an audit pack for a chosen date range and renders overrides-by-severity/MTTR/live-SLA-breach cards with a JSON download. Campaign API responses are snake_case (`CampaignRow` has no `#[serde(rename_all)]`) — the one endpoint in this codebase that isn't camelCase, called out in the frontend JS since it's an easy field-name typo trap.
- **SIEM & audit-log streaming** (`rust/crates/audit-log`, off by default): GHAS's audit log API lets a security team stream governance events into their own SIEM — Ignite's own audit trail previously lived only in `ignite.db`. `ignite_audit_log::{AuditEvent, AuditSink, dispatch}` deliver a flat event (type/summary/severity/actor/org/repo/metadata) to configured HTTPS sinks: `generic` (raw JSON POST), `splunk_hec` (`{"event": ...}` + `Authorization: Splunk <token>`), `datadog` (`DD-API-KEY` header), or `cef` (CEF-over-HTTP text body, for ArcSight-style collectors). Config: `auditLog.{enabled,sinks[].{url,kind,token}}` (`AUDIT_LOG_ENABLED`, `AUDIT_LOG_SINKS` as a JSON array env override). `AppState::emit_audit_event` (`rust/crates/server/src/state.rs`) is the server-side call point — always `tokio::spawn`'d, fire-and-forget, so a slow/unreachable SIEM endpoint never adds latency to the triggering request. Wired at four event sites: override approved + gate passed with overrides (`routes/effectivate.rs`), push rejected on unresolved blocking findings (`routes/pipeline_onboard.rs`), and API key created (the standalone `create-api-key` binary, which blocks on a throwaway tokio runtime instead of spawning, since it's a short-lived CLI that should report accurately before exiting). An S3 sink is deliberately not implemented — needs SigV4 signing, the same reason AWS was left out of `secret-verifier`; a generic HTTPS collector fronting S3 already covers that case.

## Governance-app backlog (`new_features.md`)

`new_features.md` is a 12-story backlog (US-01–US-12) evolving Ignite from an upload-oriented pipeline into a durable repository-governance app. Implemented sequentially, one story per commit, tracked here as it lands:

- **US-01 — Repository, snapshot, and scan identity (done)**: `rust/crates/db-store/src/repositories.rs` adds `repositories`/`source_snapshots`/`scan_runs` tables (`schema.rs`) alongside the original `projects`/`job_id` model — untouched, still the source of truth for every existing `jobId`/`projectId` URL. `scan_runs.legacy_project_id` is the compatibility mapping back to a `projects.id` row. `DbStore::create_project`/`finish_project`/`set_project_status` (`projects.rs`) transparently mirror every new/updated project into the new model live (`resolve_repository`/`create_or_reuse_snapshot`/`record_scan_run`/`sync_scan_run_lifecycle`); `schema::BACKFILL_REPOSITORY_MODEL_SQL` (idempotent, runs every `DbStore::open`, same posture as the pre-existing `BACKFILL_ONBOARDING_PRS_SQL`) backfills every pre-existing `projects` row that predates this feature. Repository identity prefers GitHub's numeric repository id when known (`repositories.github_repo_id`, set at zero-touch enrollment by `repository_events_webhook.rs` from the webhook payload's `repository.id`) — a rename updates the same row's `org`/`repo` in place rather than forking a new repository — and falls back to normalized `(org, repo)` equality otherwise; two different orgs with the same repo short name never merge, since the uniqueness is on the pair. A pre-existing project's true source digest was never recorded, so its backfilled snapshot gets an honestly-labeled synthetic digest (`legacy:project:<id>`/`unknown:project:<id>`), not a fabricated one — real content-addressed hashing is US-05's scope. New read endpoint `GET /api/repositories/:org/:repo` (`server/src/routes/history.rs`) is purely additive; no existing response shape changed. `is_enrollment_only` distinguishes the `repository.created`/`.transferred` webhook's zero-touch enrollment rows from actual scans. Not yet done (left to later stories per the backlog's own dependency order): a real lifecycle state machine (US-04), true content-addressed snapshot hashing (US-05), and using the new model as the primary read path for `list_onboarded_repo_summaries`/schedules (still `projects`-keyed; only additive so far, per this backlog's "preserve unrelated work" instruction).
- **US-02 — Report coverage separately from findings (done, partial breadth)**: new pure-domain crate `rust/crates/policy` (`ignite-policy`) defines `CheckOutcome` (`Completed`/`NotApplicable`/`Disabled`/`Unavailable`/`Failed`/`TimedOut`/`Cancelled`), `CheckCoverage` (per-check outcome + engine/version/fallback-flag/scope/cache-provenance), `PolicyVersion` (`legacy_compatible()` — nothing required, preserves every existing installation's gate behavior unchanged; `strict_publication()` — an explicit, curated `required_checks` list), and the one pure `evaluate_policy(coverage, has_blocking_findings, needs_review, &policy) -> PolicyDecision` (`pass`/`needs_review`/`blocked`/`incomplete`) every entry point is meant to share — 13 table-driven unit tests cover every outcome/fallback/priority combination the backlog's acceptance criteria name. Wired into `rust/crates/phase4-orchestrator`: `coverage_for_engine` maps this codebase's pre-existing `engine: &'static str` convention (already present on ~25 Phase 4 check result structs — `"disabled"`/`"failed"`/`"unconfigured"`/`"fallback"`/the real tool name — see `CLAUDE.md`'s own "full engines from fallbacks" framing) onto a `CheckCoverage`, with **no change needed to any individual check crate**; `Phase4Output.coverage: Vec<CheckCoverage>` is populated for every Phase 4 check in both fast and full mode (fast mode's skipped checks get an honest `Disabled` entry naming fast mode as the reason, not silence). `config.json`'s new `policy.strict` (`POLICY_STRICT` env override, default `false`) picks `legacy_compatible()` vs `strict_publication()`; `POST /api/pipeline/validate-all` (`server/src/routes/pipeline_validate.rs`) is the one entry point actually wired end-to-end — every response (pass **and** fail) now carries `coverage`/`policyDecision` alongside `issues`. **Not yet done** (explicitly out of scope for this pass, left as follow-up): the interactive streaming upload, onboarding, and MCP paths don't yet surface `coverage`/`policyDecision` (MCP proxies the HTTP API, so it inherits validate-all's shape once/if MCP is pointed at that response — not yet wired); Phase 3 (tests/licenses) and Phase 5 (governance CI) checks don't yet report through this envelope, only Phase 4's ~25; and there's no persisted policy-version-pinned-at-run-start yet (that's US-04's job — `evaluate_policy` itself takes a policy value with no ambient lookup, so it's ready to receive a pinned snapshot once one exists).
- **US-03 — One workflow service for every entry point (done, partial breadth)**: `rust/crates/pipeline-core` (`ignite-pipeline-core`) — previously an unused crate; every route had its own copy of the two functions it already exported instead of depending on it — is now the shared home for the phase-execution logic that `pipeline_validate.rs`, `pipeline_onboard.rs`, and `pipeline_interactive/run.rs` each carried an independent copy of: `run_license_and_dependency_scan` (Phase 3/4's manifest+LICENSE scan plus the deps.dev vulnerability check, dependency-scan-cache save included), `run_env_and_codeowners_checks` (the blocking raw-`.env*` guard plus the advisory CODEOWNERS check), and `run_governance_ci_phase` (Phase 5's `act`-tooling probe → fetch the org workflow → run it locally, returning a `GovernanceCiOutcome::{Passed,Skipped(reason)}` instead of a bare `Result<(),_>` so a caller can't mistake "local CI unavailable, non-blocking" for an unqualified pass). All three routes now call these instead of re-implementing them; `validate-all` keeps its own `tokio::join!` concurrency wrapper around `run_license_and_dependency_scan` (a real optimization, not duplicated logic) rather than losing it to unification. Fixed one real behavioral divergence the unification surfaced: `pipeline_validate.rs` used to mark Phase 5 `"skipped"` when `act`/Docker tooling was unavailable, while `pipeline_onboard.rs` and the interactive path both marked it `"success"` (with a warning that GitHub-side CI still gates the repo) — now all three agree on `"success"`, matching the majority and the actually-intended semantics (local CI is a convenience, not a required gate). `resolve_actor` also moved into `pipeline-core` behind one explicit `allow_unauth_body_actor: bool` policy flag instead of three independently-drifted copies: `validate-all` passes `true` (its documented headless-CI use case — no session, self-declared `actor.email` in the body), `onboard` passes `false` (a real provisioning+push follows, so only a verified session can attribute an override — this was already onboard's deliberate policy, previously enforced by a *different* local function than validate-all's; now it's the same function with the policy made an explicit, visible parameter). Fixed a latent gap as a side effect: onboard's overrides previously always recorded `actor_name: None` in the audit trail (its old local `resolve_actor` discarded the session's display name entirely) — now carries the real name like every other entry point. **Not yet done** (explicitly out of scope for this pass — a full `StartScan`/`CancelRun`/`SubmitReview`/`PublishApprovedSnapshot` typed-command application service, restructuring routes into thin transport adapters over it, is a much larger follow-up): Phase 1 (input validation), Phase 2 (GxP documents), Phase 4's orchestrator invocation wrapper, the override/dual-custody submission block, and Phase 6 (provisioning+ship) are still separately implemented per route — real behavioral differences exist in several of these (onboard's session-only actor policy vs. validate-all's CI fallback; the interactive path's review-gate/AI-assist/carry-forward logic has no equivalent in the synchronous routes) that need the same careful "diff it, then decide whether to unify or make the divergence an explicit parameter" treatment this pass gave Phase 3/5, not a blind merge. MCP and the CLI were already pure HTTP clients over `validate-all`/`onboard` (confirmed by grep — neither has its own `resolve_actor` or phase-loop copy), so no change was needed there.

Prerequisites for full pipeline runs: Rust (stable toolchain), `git` on PATH, `gh` CLI authenticated (`gh auth login` / `gh auth status`) with repo-create permission in the target org. Optional: `act` + Docker for Phase 5 org governance CI and for multi-language unit tests (Docker images per language). Everything else — Trivy, Semgrep, gitleaks, GuardDog, Bearer, cosign, Syft, Checkov, hadolint, jscpd, gocloc, Spectral, picklescan, oasdiff, zizmor, CodeQL, ORT, licensee — is a soft dependency: every check soft-skips to a built-in fallback (or contributes nothing) when its tool is absent. `docs-site/docs/getting-started.md` has the one-shot install script (`scripts/install-tools.sh`) for all of them.

Some tests skip a real-binary/real-network end-to-end case via an early `eprintln!("skipping: ...")` + `return` rather than failing when the corresponding tool/Docker/network isn't available — this is expected in most dev environments; the fake-CLI/offline coverage in the same test files still runs regardless.

**If a `launchd` service is managing the server locally** (`~/Library/LaunchAgents/com.ignite.server.plist`, `KeepAlive` + `WatchPaths` on the release binary — check `launchctl list | grep ignite.server`; a real PID in the first column means it's up, `-` means it's down): rebuild with `cargo build --release --manifest-path rust/Cargo.toml -p ignite-server`, then run `launchctl kickstart -k gui/$(id -u)/com.ignite.server` to make it pick up the new binary — `WatchPaths` alone isn't reliable for a cargo-rebuilt binary (observed not firing on a real rebuild), so don't just wait for it. Don't manually `pkill`/relaunch `ignite-server` yourself — if you kill it out from under launchd and then start your own copy before launchd's `KeepAlive` respawns, your ad-hoc process squats on the port and launchd's own supervised instance never comes back (shows `-` in `launchctl list` indefinitely). If that's already happened, `kill` your manual process and give launchd a few seconds to respawn on its own (confirm via `launchctl list`) rather than starting another manual one.

## Architecture

See `README.md`'s "System Architecture" diagram and "Pipeline Checks" table for the full request-flow/phase breakdown — it's accurate and Rust-only, and more detailed than what belongs here. In short: **three request paths, one set of phase-check functions** — the interactive browser upload (`POST /api/pipeline`, streaming NDJSON), the synchronous headless path used by the pre-push hook/CLI/CI (`POST /api/pipeline/validate-all`, phases 1-5 only, never ships), and the MCP path (a thin proxy from the standalone `mcp-server` binary to the same HTTP API — the MCP process itself never runs `git`/`gh`).

**File lifecycle:** upload → staging directory (per-job UUID, zip-slip/bomb-guarded extraction, isolated under the OS temp dir, `rust/crates/staging`) → scanned in place → pushed from staging → forcefully removed in a `finally`-equivalent regardless of outcome, so no user code lingers on disk.

**Issue/override model** (`rust/crates/override-engine`): raw findings from every Phase 3/4 check are normalized into a flat list of addressable issues, each with a stable id (`<category>::<file>::<line>`) and a 0-10 severity score. Blocking (`severity: error`) issues need a matching override with justification, or a source fix, to pass. Overrides require attribution and are persisted to the audit log.

**Storage** (`rust/crates/db-store`): single SQLite db (`ignite.db`, gitignored) — users, sessions, api_keys, github_connections, projects, overrides, file/CodeQL scan caches, issue baselines, runtime coverage.

**Auth** (`rust/crates/auth` + `server/src/auth*.rs`): pluggable via `AUTH_MODE` — `standalone` (scrypt-hashed accounts, default), `oidc`, or `github`. Headless callers (agents/CI) use an `Authorization: Bearer ignite_<key>` API key instead of a session cookie (`create-api-key` mints one).

## Configuration

Settings live in `config.json` at the repo root (`config.example.json` is the template, `IGNITE_CONFIG_DIR` tells the server where to find it — defaults to cwd); environment variables override individual keys — see `.env.example` for the full list. `config.json` and `.env` are both gitignored and contain this developer's real org name, SMTP creds, etc. — don't commit them.

## White-label branding (`public/branding.config.js`)

`public/index.html` never hardcodes brand values (product name, page title, header logo, support link, the `brand` accent color scale) — it reads them all from `window.IGNITE_BRAND`, defined by `public/branding.config.js` and merged over Ignite's own defaults (`DEFAULT_BRAND` in `index.html`'s `<head>`) so any key left out falls back to current Ignite branding unchanged. To apply a customer's brand, edit **only** `public/branding.config.js` — never edit brand values directly in `index.html`. This keeps the two non-conflicting: upstream feature commits touch `index.html`'s structure/logic, a customer's branding touches only their own file, and `git pull`/merge never sees the same line change on both sides. `branding.config.js` ships checked in with an empty override object (see its own header comment for every available key and an example) — the VS Code extension's own icon/name isn't covered by this and would need a separate per-customer build if ever themed too.

## Internationalization (`public/i18n.js`)

`public/index.html` supports English/French/Portuguese/German for its **static UI chrome only** — buttons, labels, headers, modals, tooltips, placeholders. Server-generated text (phase titles/logs, finding summaries/categories/severities, CWE/OWASP ids, tool output, file paths, URLs, JSON, raw API error messages) is never translated; it comes from the Rust backend and stays exactly as the API sends it. Translations live in `public/i18n.js` (`window.IGNITE_I18N.translations`), keyed by locale then by dotted key (e.g. `upload.title`), with `en` as the source of truth. `index.html` picks up a locale by two conventions — never a hardcoded literal for in-scope UI copy:
- Static markup: a `data-i18n`/`data-i18n-title`/`data-i18n-placeholder` attribute naming the key, applied by `applyStaticTranslations()`.
- JS-rendered (template-literal) markup: an inline `t('some.key', vars?)` call at the render site.

The picker (header, next to the theme toggle) calls `setLocale()`, which persists to `localStorage['ignite-locale']` and re-applies `[data-i18n*]` elements immediately; already-open dynamic panels pick up the new locale the next time their own render logic runs, not retroactively — there's no global re-render-on-locale-change. When adding new UI copy, add the key to `i18n.js`'s `en` table (and ideally fr/pt/de too — a missing key falls back to `en`, then to the raw key itself, so an incomplete translation degrades gracefully rather than breaking).

## Hardening invariants (don't relax without a strong reason)

- Every archive entry's resolved path must stay inside the staging root (zip-slip); symlink entries are skipped and never followed (`rust/crates/staging`).
- Extracted size capped at 4 GB, upload capped at 1 GB (zip-bomb guard).
- Every `git`/`gh`/external-tool invocation goes through `rust/crates/tool-runner`'s `ToolRunner`, which only ever executes as an argument array (`std::process::Command`, no shell); org/repo names are validated against GitHub's naming rules before use in any command.
- Staging directories and uploaded ZIPs are always removed regardless of success or failure.
