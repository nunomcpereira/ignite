# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Ignite is a compliance gatekeeper for onboarding code into a GitHub org. A user uploads a project (ZIP or folder) via a single-page app; the server runs it through a multi-phase pipeline - structure audit, secret scan, AI-governance audit, local LLM deep-scan, org governance CI (via `act`), unit tests - and only provisions + pushes to GitHub if every phase passes (or flagged issues are explicitly overridden with justification).

Almost all backend logic lives in one file: **`server.js`** (~6000 lines). Read it with `grep -n` for the section you need rather than loading it wholesale - it's organized as one long sequence of helper functions followed by route handlers near the bottom.

## Commands

```bash
npm install
npm start                    # → http://localhost:51337
npm test                     # node --test test/*.test.js
node --test test/secrets-scan.test.js              # single test file
node --test test/secrets-scan.test.js -t "gitleaks" # single test by name pattern

npm run guidelines:mcp       # MCP server over stdio (mcp-server.js)
npm run guidelines:mcp:http  # same, MCP_TRANSPORT=http
npm run guidelines:api       # REST API on 127.0.0.1:8090 (guidelines-api.js)
```

Prerequisites for full pipeline runs: Node ≥18, `git` on PATH, `gh` CLI authenticated (`gh auth login` / `gh auth status`) with repo-create permission in the target org. Optional: `act` + Docker for Phase 5 org governance CI and for multi-language unit tests (Docker images per language); `gitleaks` binary for supplemental secret scanning.

Also optional, all soft-dependencies feeding Phase 4 (see `checkIacSecurity`/`generateSbom`/`checkImageProvenance`/`checkSemanticSast`/`checkPiiDataFlow`/`checkCodeDuplication`/`generateLocMetrics`/`checkApiSchemas`/`checkFeaturePosture`/`checkMaliciousDependencies` in server.js): `trivy`, `checkov`, `hadolint` (IaC/container), `syft`, `cosign` (SBOM/supply-chain), `semgrep`, `bearer` (semantic/PII SAST), `jscpd`, `gocloc` (duplication/LOC metrics), `spectral` (API schema lint), `guarddog` (malicious-dependency heuristic scan, npm/PyPI). The Compliance & Feature Posture Engine (`checkFeaturePosture`) doesn't add a thirteenth binary - it reuses `semgrep`, just with its own `ignite-posture-rules.yaml` ruleset and `compliance.posture.enabled` toggle. None of these are required to run the suite or the server - every check soft-skips to a built-in fallback (or simply contributes nothing) when its tool is absent.

Some tests (gitleaks integration, the eleven external-tool/posture integration suites - `test/iac-scan.test.js`, `test/sbom-scan.test.js`, `test/cosign-scan.test.js`, `test/semgrep-scan.test.js`, `test/bearer-scan.test.js`, `test/metrics-scan.test.js`, `test/spectral-scan.test.js`, `test/posture-scan.test.js` - and the multi-language unit-test-runner tests in `test/unit-tests-multilang.test.js`) skip their real-binary end-to-end case via `t.skip()` rather than fail when the corresponding tool/Docker isn't available - this is expected in most dev environments; the fake-CLI coverage in the same files still runs regardless.

## Architecture

**Pipeline flow (server.js):** multer buffers the upload → zip-slip/bomb-guarded extraction into a per-job UUID staging dir under the OS temp dir → sequential phase checks run in place → if all pass, `git init/add/commit` + `gh repo create --private` + push from staging → staging dir and uploaded ZIP are deleted in a `finally` block regardless of outcome, so no user code lingers on disk.

**Progress transport:** the pipeline endpoint (`POST /api/pipeline`) keeps the HTTP response open and streams newline-delimited JSON events (`log`, `status`, `done`, `review_required`). The frontend (`public/index.html`) consumes this with `fetch` + `ReadableStream` - no WebSocket/polling.

**Three ways to drive the pipeline**, all sharing the same phase-check functions:
1. `POST /api/pipeline` - interactive, streaming NDJSON, used by the browser UI. Supports `dryRun` (skip provisioning/push after all checks pass) and pauses with `review_required` if overridable issues are found.
2. `POST /api/pipeline/validate-all` - synchronous JSON, phases 1-5 only (always skips shipping), takes a local `projectPath` instead of an upload. For agent/CI loops that want pass/fail without a real push.
3. MCP tool `onboard_project` (via `mcp-server.js`) - thin proxy that calls `POST /api/pipeline/onboard` on a running Ignite server; the MCP process itself never touches `git`/`gh`.

**Per-file scan caching:** Phase 4 checks (`checkSecrets`, `checkAiGovernance`, `checkLlmDeepScan` in server.js) are keyed by `{ org, repo }` passed down from the request, and cache per-file findings in the `file_scan_cache` SQLite table (`db-store.js`) keyed by `(org, repo, check_name, rel_path)` + content hash. A cache hit is a full-string match on `org` and `repo` - a typo'd or renamed repo name is a guaranteed full rescan even if the file content is identical to a previous run. The eleven external-tool checks added on top (IaC/SBOM/SAST/metrics/API-schema/malicious-dependency - see below) do **not** use this cache; each of those tools does its own whole-project discovery in one process invocation per run, so there's nothing per-file to memoize the way there is for the line-by-line regex/AST checks.

**Issue/override model (`override-engine.js`):** raw findings from secrets/governance/LLM checks (and the eleven external-tool checks below) are normalized into a flat list of addressable issues (`collectPhase4Issues`), each with a stable id (`<category>::<file>::<line>`) and a 0-10 severity score (`scoreForIssue`, independent of blocking/warning status). Blocking (`severity: "error"`) issues cannot be silently bypassed - they need a matching override with justification, or a source fix. Overrides require attribution (session user, or explicit `{email, name}` actor), trigger an email notification, and are persisted to the audit log (`overrides` table, surfaced per-project in the UI).

**Expanded diagnostic engine (IaC/supply-chain/SAST/metrics/API-schema/malicious-dependency, all inside Phase 4):** eleven optional external tools, each following the exact soft-dependency pattern gitleaks/ORT/licensee established - a `<tool>Tooling()` probe (`runTool('<tool>', ['--version'|'version'], ...)`), a `CONFIG.security|sbom|metrics|api.<tool>` block (`enabled`/`binary`/tool-specific options) with matching env-var overrides, and a check/generate function that soft-skips to a fallback (or to nothing, for tools with no meaningful heuristic substitute) on any missing-tool/parse failure:
- **IaC/container** (`checkIacSecurity`): Trivy is primary (`enabled: true` by default; falls back to a built-in Dockerfile heuristic - unpinned tag, missing `USER` - when unavailable); Checkov and hadolint are supplements merged in and deduped by `file+line+kind` (not line alone - different tools' rule catalogs routinely flag distinct issues on the same line).
- **SBOM** (`generateSbom`): Syft generates a CycloneDX SBOM, attached as a downloadable project document (`store.addUploadDocument`) - never an issue. Falls back to a minimal manifest-derived component list.
- **Image provenance** (`checkImageProvenance`): cosign verifies Sigstore signatures on Dockerfile `FROM` base images (on by default - a real network call per unique image, so `COSIGN_ENABLED=false` is there to opt out); unsigned images are always advisory.
- **Semantic SAST** (`checkSemanticSast`): Semgrep OSS, ruleset configurable (`security.semgrep.config`, default `p/security-audit`).
- **PII/GDPR data-flow** (`checkPiiDataFlow`): Bearer (on by default); needs real git remote/branch context that a fresh ZIP/folder upload doesn't have, so `ensureGitContextForBearer` bootstraps a throwaway one (init/commit + fake `origin` + `refs/remotes/origin/HEAD`) before invoking it. `bearer scan` with no `--report` flag defaults to Bearer's general "security" report (broad SAST - path traversal, weak crypto, etc.), not privacy-specific - findings are filtered to only those Bearer itself tags `category_groups: ["PII", ...]`, so a generic non-PII security finding never gets mislabeled as `pii-dataflow` (those already duplicate Semgrep's job).
- **Code duplication** (`checkCodeDuplication`): jscpd (off by default - the one exception among these ten; toggle via `metrics.jscpd.enabled`/`JSCPD_ENABLED`), always advisory (never blocks a run).
- **LOC metrics** (`generateLocMetrics`): gocloc, purely descriptive - attached as a document like the SBOM, never an issue.
- **API schema lint** (`checkApiSchemas`): Spectral has no directory-scan mode, so `discoverApiSchemaFiles` content-sniffs `.yaml`/`.yml`/`.json` files for a top-level `openapi`/`swagger`/`asyncapi` key rather than relying on filename. Ruleset defaults to the bundled `spectral-default-ruleset.yaml` (`spectral:oas` + `spectral:asyncapi`), overridable via `api.spectral.ruleset`/`SPECTRAL_RULESET`.
- **Compliance & Feature Posture Engine** (`checkFeaturePosture`, `CONFIG.compliance.posture`): reuses Semgrep's binary with a dedicated ruleset (`ignite-posture-rules.yaml`, `languages: [generic]` `pattern-regex`) to classify presence - not vulnerabilities - of SSO/RBAC/audit-logging/TLS/backups/encryption/rate-limiting as `DETECTED`/`PARTIAL`/`MISSING`. Never an issue; attached as `posture-report.json`. Falls back to `checkFeaturePostureFallback` (same weak/strong model, JS regex) when Semgrep is disabled/missing.

Every one of checkov/cosign/bearer is **on by default** (flipped from their original off-by-default rollout) - set `CHECKOV_ENABLED`/`COSIGN_ENABLED`/`BEARER_ENABLED` to `false` individually to opt back out. `guarddog` (malicious-dependency heuristic scan, npm/PyPI) is likewise **on by default** - set `GUARDDOG_ENABLED=false` to opt out; it's the heaviest of the twelve (a real per-dependency registry fetch + static inspection), so environments with many manifest dependencies should expect Phase 4 to take noticeably longer with it on.

**Path canonicalization gotcha (`relativeToRoot` helper, server.js):** external tools report their finding's file path inconsistently - some canonicize symlinks in the staging path (macOS's `/tmp` → `/private/tmp`, `/var` → `/private/var`; Spectral does this), others echo back exactly whatever path/cwd they were invoked with, uncanonicalized (Semgrep, in both `checkSemanticSast` and `checkFeaturePosture`). Diffing an uncanonicalized `root` against a canonicalized tool-reported path (or vice versa) produces a technically-valid but useless multi-`../` relative path - hit for real via a live pipeline run at the `/private/var/folders/...` staging root, not just theoretically. `relativeToRoot(root, targetPath)` fixes it once, generically, by `realpath`-ing *both* sides before computing the relative path - reach for it (not a bespoke `path.relative(root, path.resolve(root, ...))`) any time you're turning an external tool's reported path into a project-relative one.

**Ignite Studio's top bar surfaces every connected tool's output in one place** (`public/index.html`): a 📄 SBOM / 📊 LOC Metrics / 🛡️ Posture button per non-issue artifact (each backed by a new on-demand `GET /api/pipeline/:jobId/studio/{sbom,loc-metrics,posture}` endpoint, same live-recompute pattern the pre-existing 📦 Dependencies button uses), plus the project-wide issue summary bar's per-category labels became clickable filters (`studioSetCategoryFilter`) that narrow the file tree to one category's findings at a time - covering the other seven tools, whose findings already flowed into the same issue list secrets/AI-governance findings use.
- **Compliance & Feature Posture Engine** (`checkFeaturePosture`, `CONFIG.compliance.posture`): a different kind of check from the other nine - it classifies the *presence* of security/compliance features (SSO/SAML/OIDC, RBAC/ABAC, audit logging, SIEM forwarding, HTTPS/TLS, backups/DR, encryption at rest, rate limiting) as `DETECTED`/`PARTIAL`/`MISSING` per category, not error/warning issues, so it never feeds `collectPhase4Issues` - it's attached as a `posture-report.json` document instead (same as the SBOM/LOC-metrics artifacts). Fully conditioned on Semgrep (reuses `security.semgrep`'s binary/tooling probe - same CLI, a dedicated ruleset `ignite-posture-rules.yaml` and its own `compliance.posture.enabled` toggle): `>=1` "strong" (confirmed usage, e.g. `@PreAuthorize(`) match in a category is `DETECTED`; only "weak" (import/dependency-only) matches is `PARTIAL`; none is `MISSING`. `ignite-posture-rules.yaml` uses Semgrep's `languages: [generic]` `pattern-regex` mode deliberately - the question being answered ("does this codebase use framework X") is the same across all six target languages (TS/JS, Java, Go, Python, C#, Ruby), so one cross-language text-signature rule per category/tier is more maintainable than six near-duplicate AST rules. Soft-falls back to `checkFeaturePostureFallback` - the same weak/strong model as a JS regex sweep, kept in sync by hand - when Semgrep is disabled or not installed, logged as `Engine: Ignite Built-In Posture Scanner (Fallback)` vs. `Engine: Semgrep CLI vX.X (External Posture Scanner)`.

All twelve checks (eleven external tools, plus the posture engine that reuses Semgrep's binary rather than adding a twelfth) wire into the same three call sites `checkSecrets`/`checkAiGovernance` already do (`/api/pipeline/validate-all`, `/api/pipeline/onboard`, the interactive SSE pipeline) plus `/api/tools/status` and the UI's `TOOLS_META` panel in `public/index.html` - never Studio's rescan endpoint (network/process-heavy tools would make every edit-loop rescan slow). Each has its own test file (`test/iac-scan.test.js`, `test/sbom-scan.test.js`, `test/cosign-scan.test.js`, `test/semgrep-scan.test.js`, `test/bearer-scan.test.js`, `test/metrics-scan.test.js`, `test/spectral-scan.test.js`, `test/posture-scan.test.js`, `test/guarddog-scan.test.js`) covering config/env wiring, fake-CLI parsing/dedup/soft-fail, and a real-binary end-to-end case that self-skips when the tool isn't installed.

**Auth (`auth.js`):** pluggable via `AUTH_MODE` (env) / `auth.mode` (config.json) - `standalone` (local scrypt-hashed accounts, default), `oidc` (delegates to any standards-compliant IdP), or `github` (sign in with GitHub, which also connects that account for push). All modes converge on the same session-cookie + `req.user` shape that override attribution relies on. Auth is not required to browse or run the pipeline - only enforced where attribution matters (submitting an override without a session needs an explicit actor in the body, else `401`).

**Guidelines catalog (`guidelines/catalog.js` + `guidelines/checks.js`):** the same detection patterns Ignite's onboarding pipeline enforces (secret regex, AI-governance `.invoke()`/`.stream()` calls missing `recursion_limit`, injection sinks, insecure deserialization, etc.), exposed as a standalone checks engine so they can be applied during development, not just at onboarding. Consumed by `mcp-server.js` (MCP tools: `list_guidelines`, `get_guideline`, `check_guidelines`, `check_project`, `onboard_project`) and `guidelines-api.js` (REST equivalent, loopback-only by default since `/check-project` reads arbitrary host paths).

**Storage (`db-store.js`):** single SQLite db (`ignite.db`, gitignored) holding users, sessions, github_connections, projects, overrides, and the file_scan_cache - all accessed through prepared statements returned by `createDbStore()`.

**Phase 4 org governance CI:** rather than reimplementing the central org's workflow logic, Ignite fetches the real `ai-guardrails-orchestrator.yml` from the governance repo via `gh api` and runs it locally with `act` against the staged project in Docker - so local pass/fail matches what a real PR would get. Soft-skips with a warning if `act`/Docker are unavailable (the workflows still gate remotely).

## Configuration

Settings live in `config.json` next to `server.js` (`config.example.json` is the template); environment variables override individual keys - see `.env.example` for the full list (LLM scan URL/model/mode, governance repo/workflow, gitleaks toggle, SMTP/notifications, auth mode/OIDC settings, the eleven external-tool `enabled`/`binary`/tool-specific settings under `security.*`/`sbom.syft`/`metrics.*`/`api.spectral`, etc.). `config.json` and `.env` are both gitignored and contain this developer's real org name, SMTP creds, etc. - don't commit them.

## Hardening invariants (don't relax without a strong reason)

- Every archive entry's resolved path must stay inside the staging root (zip-slip); symlink entries are skipped and never followed.
- Extracted size capped at 1 GB, upload capped at 250 MB (zip-bomb guard).
- All `git`/`gh` invocations use `execFile` with argument arrays (no shell); org/repo names are validated against GitHub's naming rules before use in any command.
- Staging directories and uploaded ZIPs are always removed in a `finally` block, success or failure.
